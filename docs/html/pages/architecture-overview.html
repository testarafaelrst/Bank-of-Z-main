Architecture Overview

Bank of Z uses a hybrid architecture that combines modern web technologies with IBM Z transaction-processing systems. The application provides a browser-based interface that communicates with backend services through z/OS Connect, routing requests to CICS or IMS Transaction Manager (IMS TM) depending on the transaction path. This architecture demonstrates how multiple IBM Z technologies can be combined to deliver a unified, modern banking application experience while supporting contemporary development and deployment practices.

1. Overview

Bank of Z is a full-stack banking application built on IBM Z infrastructure. It integrates a modern browser-based frontend with robust, enterprise-grade backend systems, exposing banking operations through RESTful APIs provided by z/OS Connect. Although the underlying transaction-processing path may differ per operation, users interact with a single, consistent web interface.

The application brings together the following core technologies:

Component Role
Browser-based UI User-facing web interface for banking operations
z/OS Connect API gateway bridging modern web requests to IBM Z services
CICS Transaction processing for one set of banking operations
IMS Transaction Manager (IMS TM) Transaction processing for an alternate set of banking operations
Db2 for z/OS Relational database for banking data
IMS Databases Hierarchical database for banking data
IBM MQ Asynchronous messaging and external system integration
IBM Z DevSecOps Tooling Development, build, and deployment pipelines

This hybrid approach allows Bank of Z to leverage the performance, reliability, and security characteristics of IBM Z while remaining accessible through standard web technologies and modern API patterns.

2. System Architecture

The Bank of Z system architecture is organized in layers, from the user-facing web interface down through the API gateway, transaction-processing environments, data stores, and external integrations. The diagram below illustrates how these layers relate to one another.

The diagram above shows the two primary transaction-processing paths — CICS and IMS TM — both accessible from the same z/OS Connect API layer. Depending on the banking operation being invoked, a request is routed to the appropriate transaction environment, which in turn executes application logic and accesses the relevant data store.

3. Component Details

3.1 Browser-based User Interface

The frontend is a modern web application delivered to the user’s browser. It communicates exclusively with the z/OS Connect API layer using standard HTTP/REST calls, keeping the UI decoupled from the underlying IBM Z transaction systems. Users experience a single, consistent banking application regardless of which backend path handles their request.

3.2 z/OS Connect

z/OS Connect acts as the API gateway for the entire application. It exposes RESTful APIs to the browser-based UI and routes incoming requests to the appropriate backend transaction environment — either CICS or IMS TM. This component is central to the hybrid architecture, bridging modern web standards with IBM Z transaction processing.

z/OS Connect provides:

  • RESTful API exposure for banking operations
  • Request routing to CICS or IMS TM
  • API definition and lifecycle management
  • Security and authentication enforcement at the gateway layer

3.3 CICS Transaction Processing

CICS (Customer Information Control System) handles one set of banking transaction paths within Bank of Z. Application logic within CICS is implemented in COBOL and accesses Db2 for z/OS for relational data storage. CICS also integrates with IBM MQ for asynchronous messaging and external system communication.

Key characteristics of the CICS path:

  • COBOL application programs execute within the CICS transaction environment
  • Db2 for z/OS is the primary data store for this path
  • IBM MQ enables integration with external systems and asynchronous operations

3.4 IMS Transaction Manager (IMS TM)

IMS Transaction Manager provides an alternative transaction-processing path within Bank of Z. Application programs running under IMS TM access IMS databases for hierarchical data storage. Like the CICS path, IMS TM also integrates with IBM MQ for messaging.

Key characteristics of the IMS TM path:

  • IMS application programs execute within the IMS TM environment
  • IMS databases serve as the primary data store for this path
  • IBM MQ enables messaging and external system integration

3.5 Db2 for z/OS

Db2 for z/OS provides relational database services for the CICS transaction path. Banking data accessed through CICS transactions — such as account balances, customer records, and transaction history — is stored and retrieved from Db2. COBOL programs interact with Db2 using embedded SQL statements.

Example of an embedded SQL query in COBOL:

COBOL 
EXEC SQL
    SELECT ACCOUNT_BALANCE
    INTO   :WS-ACCOUNT-BALANCE
    FROM   ACCOUNT
    WHERE  ACCOUNT_ID = :WS-ACCOUNT-ID
END-EXEC.

3.6 IMS Databases

IMS databases provide hierarchical data storage for the IMS TM transaction path. They store banking data accessed by IMS application programs and are well-suited to high-throughput, structured banking record access patterns.

3.7 IBM MQ

IBM MQ provides asynchronous messaging capabilities shared by both transaction-processing paths. It enables Bank of Z to integrate with external systems and supports decoupled, reliable communication between components. Both CICS and IMS TM paths can produce and consume messages via IBM MQ.

3.8 IBM Z DevSecOps Tooling

Bank of Z is built with a DevSecOps approach, using IBM Z-native tooling to support development, testing, security scanning, and deployment pipelines. This ensures that the application can be maintained and evolved using modern software delivery practices while targeting IBM Z as the deployment platform.

4. Data Flow

The following sequence diagram illustrates a typical banking operation request flowing through the Bank of Z architecture, from the user’s browser through to data retrieval and response.

sequenceDiagram participant User as Browser / User participant UI as Web UI participant ZC as z/OS Connect participant CICS as CICS / IMS TM participant App as COBOL / IMS App Program participant DB as Db2 / IMS Database participant MQ as IBM MQ User->>UI: Initiates banking operation UI->>ZC: HTTP REST API Request ZC->>CICS: Routes request to transaction environment CICS->>App: Invokes application program App->>DB: Executes data query / update DB-->>App: Returns data App->>MQ: Publishes message (if required) MQ-->>App: Acknowledgement App-->>CICS: Returns result CICS-->>ZC: Transaction response ZC-->>UI: HTTP REST API Response UI-->>User: Displays result

This flow highlights the clean separation of concerns across layers:

  1. The UI layer handles only presentation and user interaction.
  2. z/OS Connect manages API exposure, routing, and security at the gateway level.
  3. CICS or IMS TM manages transaction lifecycle, program invocation, and resource coordination.
  4. Application programs (COBOL or IMS) contain the business logic and data access operations.
  5. Db2 or IMS databases provide persistent data storage.
  6. IBM MQ enables asynchronous and external system integration when required.

5. Transaction Processing Paths

Bank of Z supports two distinct transaction-processing paths. While users experience a unified application, the underlying execution environment differs depending on the operation.

graph LR A[z/OS Connect] --> B{Route Decision} B -->|CICS Path| C[CICS] B -->|IMS Path| D[IMS TM] C --> E[COBOL Programs] E --> F[Db2 for z/OS] E --> G[IBM MQ] D --> H[IMS Application Programs] H --> I[IMS Databases] H --> G

Both paths share IBM MQ as a common integration point, allowing either transaction environment to participate in asynchronous messaging and external system communication. The dual-path design demonstrates how an IBM Z application can support multiple transaction-processing technologies within a single, unified solution.

6. DevSecOps Integration

Bank of Z is designed to support modern software delivery workflows using IBM Z DevSecOps tooling. This includes:

  • Source control and version management for COBOL, JCL, and configuration assets
  • Automated build and compile pipelines for z/OS application artifacts
  • Security scanning integrated into the development pipeline
  • Automated testing for transaction programs and API endpoints
  • Deployment automation targeting the IBM Z environment

This DevSecOps integration ensures that Bank of Z can be maintained, extended, and deployed with the same velocity and quality standards expected of modern cloud-native applications, while retaining the enterprise-grade reliability of IBM Z.
