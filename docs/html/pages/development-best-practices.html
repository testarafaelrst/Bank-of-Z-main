Development Best Practices

This page documents recommended practices for developing, testing, and maintaining IBM Z applications within the Bank of Z project. Following these guidelines helps ensure consistent, reliable, and maintainable code across all contributors and environments.

1. Overview

The Bank of Z project follows a structured development approach designed to support IBM Z application development using modern DevOps tooling. These best practices cover branch management, workspace configuration, change validation, source organization, and workflow selection.

Adhering to these recommendations reduces integration risk, improves code quality, and ensures that all contributors work from a consistent and well-understood baseline. Whether you are developing COBOL programs, copybooks, BMS maps, web applications, or z/OS Connect artifacts, these practices apply across the full scope of Bank of Z development activities.

2. System Architecture

The Bank of Z development environment is composed of several interconnected layers — from local developer workspaces through version control and CI/CD pipelines, to the IBM Z target environment. Understanding how these components relate helps developers make informed decisions about where changes are made, how they are validated, and how they are promoted.

The diagram above illustrates the end-to-end development flow. Developers begin work on isolated branches from their local workstations, commit changes to version control, select the appropriate workflow, and promote validated changes through the build and deploy pipeline to the IBM Z target environment.

3. Branch Management

3.1 Work in Isolated Branches

Create a dedicated branch for each feature, enhancement, or defect fix. Isolating changes makes it easier to review, test, and manage updates before they are merged into the main code line.

graph LR A[Main Branch] -->|Branch off| B[Feature Branch] A -->|Branch off| C[Bugfix Branch] A -->|Branch off| D[Enhancement Branch] B -->|Pull Request & Review| A C -->|Pull Request & Review| A D -->|Pull Request & Review| A

This branching model ensures that the main code line always reflects a stable, reviewed state. Each branch represents a single, well-scoped unit of work, making reviews more focused and reducing the risk of unintended side effects.

3.2 Synchronize Regularly

Keep your local workspace synchronized with the latest project changes to reduce merge conflicts and ensure that development is based on the most current source.

BASH 
# Fetch latest changes and rebase your feature branch
git fetch origin
git rebase origin/main

Regular synchronization prevents long-lived branches from diverging significantly from the main code line, which reduces integration complexity and merge conflict frequency.

4. Workspace Configuration

4.1 Keep Your Workspace Configuration Up to Date

Review your setup configuration before starting development activities. Ensure that paths, environment settings, and required dependencies match your target environment.

If configuration values change, update your local environment before running setup or deployment tasks. Outdated configuration is a common source of build failures and environment inconsistencies.

YAML 
# Example: Validate key environment settings before starting work
environment:
  COBOL_SOURCE_DIR: /path/to/cobol/src
  COPYBOOK_DIR: /path/to/copybooks
  TARGET_HLQ: USER.BANKOFZ
  ZOWE_PROFILE: bankofz-dev

4.2 Review Setup Output

Monitor workflow output and setup logs during development activities. Review any warnings or errors before proceeding to the next task. Ignoring warnings can allow configuration drift or unresolved dependencies to compound across multiple development cycles.

5. Change Management

5.1 Make Small, Incremental Changes

Implement and validate changes in small increments rather than making large updates at once. Smaller changes are easier to test, troubleshoot, and review.

graph TD A[Identify Task] --> B[Implement Small Change] B --> C[Validate Locally] C -->|Pass| D[Commit to Branch] C -->|Fail| B D --> E[Run Build & Deploy Workflow] E -->|Pass| F[Proceed to Next Increment] E -->|Fail| G[Review Logs & Fix] G --> B

The diagram above illustrates the incremental development loop. Each change is scoped, validated, and committed before the next increment begins. This discipline keeps the feedback loop tight and issues isolated.

5.2 Validate Changes Frequently

Run the appropriate setup and deployment workflow after making changes to verify that updates build and deploy successfully. Early validation helps identify issues before they affect additional development work.

BASH 
# Example: Trigger a Zowe CLI-based build and deploy after changes
zowe jobs submit ds "USER.BANKOFZ.JCL(BLDEPLOY)" --wfo

5.3 Keep Source Changes Organized

Store application updates in the appropriate source directories and follow established project conventions for all artifact types.

Artifact Type Source Directory Convention
COBOL Programs /src/cobol/
Copybooks /src/copybooks/
BMS Maps /src/bms/
Web Applications /src/web/
z/OS Connect Artifacts /src/zosconnect/

Maintaining consistent directory structures allows automated pipelines to locate and process source files reliably without manual intervention.

6. Documentation

6.1 Document Significant Changes

Update relevant documentation when introducing new functionality, modifying configuration requirements, or changing development processes. Keeping documentation current helps other contributors understand and use your changes.

Examples of changes that warrant documentation updates include:

  • New features or programs — Describe purpose, inputs, outputs, and dependencies.
  • Configuration changes — Note updated paths, profile names, or environment variables.
  • Process changes — Update workflow instructions or development guides as needed.

7. Workflow Selection

7.1 Use the Workflow That Matches Your Development Needs

Selecting the appropriate workflow improves development efficiency and reduces turnaround time during testing. Bank of Z supports two primary development workflows:

Workflow Best Used When
Zowe CLI Working with branch-based development and version-controlled changes
GRUB Rapidly testing local changes without committing them first
sequenceDiagram participant Dev as Developer participant VCS as Version Control participant Zowe as Zowe CLI Workflow participant GRUB as GRUB Workflow participant Z as IBM Z Environment Dev->>Dev: Make source changes alt Branch-based development Dev->>VCS: Commit changes to feature branch VCS->>Zowe: Trigger build & deploy Zowe->>Z: Deploy validated artifacts Z-->>Dev: Deployment result else Rapid local testing Dev->>GRUB: Submit local changes directly GRUB->>Z: Deploy without commit Z-->>Dev: Test result Dev->>VCS: Commit once satisfied end

The sequence diagram above shows the decision point between the two workflows. Use the Zowe CLI workflow when your changes are ready for version control and you want the full pipeline validation cycle. Use the GRUB workflow when you need fast iteration on local changes before formalizing them in a commit.

8. Summary of Best Practices

The following table consolidates all recommended practices for quick reference:

# Practice Key Benefit
1 Work in isolated branches Simplifies review, testing, and merging
2 Keep workspace configuration current Prevents build failures and environment drift
3 Make small, incremental changes Easier to test, troubleshoot, and review
4 Validate changes frequently Catches issues early in the development cycle
5 Keep source changes organized Enables reliable automated pipeline processing
6 Review setup output and logs Identifies warnings before they become failures
7 Synchronize regularly Reduces merge conflicts and integration risk
8 Document significant changes Supports contributor understanding and onboarding
