Deploying Bank of Z

Bank of Z provisions a complete application environment on z/OS, including CICS, IMS, z/OS Connect, a Liberty frontend server, and all application data. The deployment process is fully automated once you have cloned the repository and configured it for your environment. Three deployment workflows are supported, all of which run the same underlying stages and produce the same deployed environment.

1. Overview

Deploying Bank of Z sets up the full application stack on z/OS from source. The process is divided into three sequential stages that are consistent across all deployment methods:

  1. Validate prerequisites — Confirms required tools and connectivity are available on z/OS USS.
  2. Provision middleware — Stops any existing instances, cleans up datasets, and provisions CICS, IMS, z/OS Connect, Db2 tables, and the Liberty frontend server.
  3. Build and deploy — Compiles all application sources using DBB, packages the outputs, deploys via Wazi Deploy, and loads test data into Db2 and IMS.

The initial build and deployment typically takes 15 to 20 minutes. After the initial deployment is complete, incremental builds can be used for day-to-day development, rebuilding and redeploying only the components affected by source changes.

All three workflows invoke the same script entry points:

BASH 
.setup/setup-common.sh validate-prereqs
.setup/setup-common.sh environment
.setup/setup-common.sh install-bank-of-z

2. System Architecture

The diagram below illustrates the high-level components provisioned by a Bank of Z deployment and how they relate to each other at runtime.

graph TD User["👤 User / Browser"] FE["Liberty Frontend Server\n(HTTP :9080 / HTTPS :9444)"] ZC["z/OS Connect\nEnterprise Edition"] CICS["CICS Region\n(COBOL / PL/I / Assembler / BMS)"] IMS["IMS Region\n(IMS TM + IMS DB)"] DB2["Db2 for z/OS\n(DBD1 subsystem)"] MQ["IBM MQ"] User -->|HTTP/HTTPS| FE FE -->|REST API| ZC ZC -->|CICS Link| CICS ZC -->|IMS Connect| IMS CICS -->|SQL| DB2 IMS -->|DL/I| DB2 CICS -->|MQ| MQ IMS -->|MQ| MQ

The Liberty frontend server acts as the entry point for browser traffic. It delegates business logic calls to z/OS Connect, which routes them to the appropriate CICS or IMS backend region. Both CICS and IMS interact with Db2 for persistent data storage, and IBM MQ is used for asynchronous messaging between components.

3. Deployment Workflows

Bank of Z supports three deployment workflows. Each workflow runs the same three stages and produces an identical deployed environment. Choose the workflow that best fits your tooling and access model.

Workflow Where you run scripts Requires SSH to USS Requires push to remote
Direct USS On z/OS USS directly ✅ Yes ❌ No
Zowe CLI On your local machine ❌ No ✅ Yes
GRUB On your local machine ❌ No ❌ No

4. Deploy Using Direct USS Access

Use this method to connect directly to z/OS via SSH and run each deployment stage manually. This is the most transparent option because you can observe every step of the process in real time.

Before you begin, ensure that you have:

  • SSH access to your z/OS system
  • Git installed on z/OS USS
  • A z/OS environment that meets the prerequisites

The following sequence diagram shows the flow of operations for the direct USS deployment:

sequenceDiagram actor Dev as Developer participant USS as z/OS USS participant DB2 as Db2 participant CICS as CICS Region participant IMS as IMS Region participant ZC as z/OS Connect participant FE as Liberty Frontend Dev->>USS: SSH login Dev->>USS: git clone repository Dev->>USS: vi .setup/config/config.yaml Dev->>USS: setup-common.sh validate-prereqs USS-->>Dev: Prereqs validated ✅ Dev->>USS: setup-common.sh environment USS->>DB2: Create Db2 tables USS->>CICS: Provision CICS region (zconfig) USS->>IMS: Provision IMS region + DB (zconfig) USS->>ZC: Create and start z/OS Connect server USS->>FE: Create and start Liberty frontend USS-->>Dev: Middleware provisioned ✅ Dev->>USS: setup-common.sh install-bank-of-z USS->>USS: DBB full build (COBOL, PL/I, ASM, BMS, Java) USS->>USS: Package build outputs USS->>CICS: Wazi Deploy → CICS USS->>IMS: Wazi Deploy → IMS USS->>DB2: Populate test data USS->>IMS: Populate IMS test data USS-->>Dev: Deployment complete ✅ Dev->>FE: Open browser → verify

4.1 SSH to z/OS

BASH 
ssh user@your-zos-host

4.2 Clone the Repository

Choose a working directory on USS. You will reference this path in the configuration file.

BASH 
export BANK_OF_Z_WORK_DIR=/usr/local/sandboxes/bank-of-z
mkdir -p $BANK_OF_Z_WORK_DIR
cd $BANK_OF_Z_WORK_DIR
git clone https://github.com/IBM/Bank-of-Z.git
cd Bank-of-Z

4.3 Edit the Configuration File

Open the configuration file in your USS editor and update it for your environment:

BASH 
vi .setup/config/config.yaml

For information about each configuration field, see the Environment Configuration documentation.

4.4 Validate Prerequisites

BASH 
.setup/setup-common.sh validate-prereqs

Verifies that all required tools are installed at the required versions. Resolve any failures before continuing.

4.5 Provision Middleware

BASH 
.setup/setup-common.sh environment

Provisions the complete application runtime, including Db2 tables, a CICS region, an IMS region and database, a z/OS Connect server, and the Liberty frontend server. This stage performs the following in sequence:

  1. Stops any existing Bank of Z tasks (CICS, IMS, z/OS Connect, frontend)
  2. Cleans up existing application datasets
  3. Clones the IBM DBB accelerators repository from GitHub
  4. Copies the zBuilder build framework
  5. Creates Db2 database tables
  6. Provisions a CICS region using zconfig
  7. Provisions an IMS region using zconfig
  8. Creates IMS database objects
  9. Starts IMS Bank of Z message processing regions
  10. Creates and starts a z/OS Connect server
  11. Creates and starts a frontend Liberty server

Note: This stage requires a pre-existing Db2 subsystem (DBD1). All other middleware is provisioned automatically.

4.6 Build and Deploy

BASH 
.setup/setup-common.sh install-bank-of-z

Runs a complete DBB build, packages the outputs, deploys via Wazi Deploy, and populates Db2 and IMS with test data. The initial build and deployment typically takes 15 to 20 minutes.

Note: Warnings related to the YAML scanner and chown failures are expected and do not indicate a problem.

4.7 Verify the Deployment

Open the Bank of Z frontend in a browser:

HTTP

CODE 
http://<your-zos-host>:9081/admin.html

HTTPS

CODE 
https://<your-zos-host>:9445/admin.html

4.8 Run Post-Install Verification Tests

BASH 
.setup/setup-common.sh verify-installation

Runs the integration test suite in tests/ against the deployed application. The tests exercise the CICS and IMS API paths and report a pass/fail result for each. All tests must pass before the installation is considered complete.

5. Deploy Using Zowe CLI

Use this method to deploy Bank of Z from your local machine using Zowe CLI. The script clones your current branch from GitHub onto z/OS USS and runs all three setup stages automatically — no SSH access to USS is required.

Before you begin, ensure that:

  • Your z/OS environment meets the prerequisites
  • Zowe CLI is installed on your local machine
  • The RSE API plug-in is installed and your Zowe profile is configured

The diagram below shows how the Zowe CLI workflow orchestrates the deployment from a local machine to z/OS:

graph TD A["👤 Developer\n(Local Machine)"] -->|"git clone"| B["Local Repository"] B -->|"Edit config.yaml"| C["Configured Local Repo"] C -->|"git push to remote"| D["GitHub Remote Branch"] C -->|"bash .setup/setup-local.sh"| E["Zowe CLI Script"] E -->|"RSE API: Create USS workspace"| F["z/OS USS Workspace"] D -->|"git clone from GitHub"| F F -->|"setup-remote.sh"| G["validate-prereqs"] G --> H["environment\n(Provision Middleware)"] H --> I["install-bank-of-z\n(Build + Deploy)"] I --> J["✅ Bank of Z Running"]

Because the Zowe CLI script clones from the GitHub remote, your branch must be pushed before running the script. Any local commits that have not been pushed will not be included in the deployed environment.

5.1 Clone the Repository Locally

BASH 
git clone https://github.com/IBM/Bank-of-Z.git
cd Bank-of-Z

5.2 Edit the Configuration File

Open .setup/config/config.yaml in your local editor and update it for your environment.

5.3 Push Your Branch

The script detects your current local branch and clones it from GitHub to z/OS USS. Your branch must be pushed to the remote before running the script.

BASH 
git add .setup/config/config.yaml
git commit -m "Configure for my environment"
git push

5.4 Run the Setup Script

BASH 
bash .setup/setup-local.sh

Alternatively, in Visual Studio Code, select Command Palette → Tasks: Run Task → Setup Bank of Z Environment.

5.5 What Runs Automatically

The script runs the following stages:

  1. Creates the USS workspace directory using the Zowe RSE API.
  2. Clones your current branch from GitHub to z/OS USS.
  3. Invokes setup-remote.sh on USS, which runs the following stages:
    • validate-prereqs — Verifies that all required tools are installed on USS.
    • environment — Provisions Db2, CICS, IMS, z/OS Connect, and the frontend server.
    • install-bank-of-z — Builds the application, deploys it using Wazi Deploy, and populates test data.

The initial deployment typically takes 15 to 20 minutes. Logs are written to /tmp/remote-setup.log on your local machine.

Note: Warnings related to the YAML scanner and chown failures are expected and do not indicate a problem.

5.6 Verify the Deployment

Open the Bank of Z frontend in a browser:

CODE 
http://<your-zos-host>:9080/bank-frontend-vanilla

6. Deploy Using GRUB

Use this method to deploy Bank of Z using GRUB. GRUB syncs your local file changes directly to z/OS USS and triggers the setup scripts automatically via a post-sync hook. You do not need to commit or push your changes before deploying.

Before you begin, ensure that:

  • Your z/OS environment meets the prerequisites
  • GRUB is installed and configured with the Bank of Z remote path and post-sync hook

The diagram below shows how GRUB transfers files and triggers the deployment pipeline:

sequenceDiagram actor Dev as Developer participant Local as Local Machine participant GRUB as GRUB Sync Engine participant USS as z/OS USS participant Scripts as setup-remote.sh Dev->>Local: Edit config.yaml (no commit needed) Dev->>GRUB: Trigger GRUB sync GRUB->>USS: Transfer changed files to USS workspace USS-->>GRUB: Sync complete GRUB->>USS: Invoke post-sync hook USS->>Scripts: Run setup-remote.sh Scripts->>USS: validate-prereqs Scripts->>USS: environment (provision middleware) Scripts->>USS: install-bank-of-z (build + deploy) USS-->>Dev: Deployment complete ✅

GRUB only transfers files that have changed since the previous sync, making subsequent deployments faster. Because files are synced directly from your local workspace, there is no need to commit or push changes to a remote repository before deploying.

6.1 Clone the Repository Locally

BASH 
git clone https://github.com/IBM/Bank-of-Z.git
cd Bank-of-Z

6.2 Edit the Configuration File

Open .setup/config/config.yaml in your local editor and update it for your environment.

You do not need to commit your changes after editing. GRUB syncs the file as-is directly to z/OS USS.

6.3 Trigger a GRUB Sync

Trigger a GRUB sync from your local machine. Refer to the GRUB documentation for the specific command or UI action for your installation.

GRUB transfers your local changes to z/OS USS. Only files that have changed since the previous sync are transferred.

6.4 What Runs Automatically

After the sync completes, the configured post-sync hook runs setup-remote.sh on z/OS USS. The script runs the following setup stages automatically:

  • validate-prereqs — Verifies that all required tools are installed on USS.
  • environment — Provisions Db2, CICS, IMS, z/OS Connect, and the frontend server.
  • install-bank-of-z — Builds the application, deploys it using Wazi Deploy, and populates test data.

The initial deployment typically takes 15 to 20 minutes. Subsequent syncs are typically faster because only changed files are transferred.

6.5 Verify the Deployment

Open the Bank of Z frontend in a browser:

CODE 
http://<your-zos-host>:9080/bank-frontend-vanilla

7. Deployment Stages Reference

All three workflows run the same three stages, each invoked as a subcommand of .setup/setup-common.sh. The following diagram illustrates the sequential relationship between the stages.

graph LR A["🔍 Stage 1\nvalidate-prereqs\n(.setup/setup-common.sh)"] B["⚙️ Stage 2\nenvironment\n(.setup/setup-common.sh)"] C["🚀 Stage 3\ninstall-bank-of-z\n(.setup/setup-common.sh)"] A -->|"Prerequisites met"| B B -->|"Middleware provisioned"| C C -->|"Build + Deploy complete"| D["✅ Bank of Z\nDeployed"]

7.1 Stage 1: Validate Prerequisites

BASH 
.setup/setup-common.sh validate-prereqs

Verifies that all required tools are installed on z/OS USS at the versions specified in config.yaml. This includes:

  • DBB
  • ZOAU
  • zconfig
  • Wazi Deploy
  • Java
  • Git
  • Network connectivity to GitHub

Resolve any reported failures before proceeding to Stage 2.

7.2 Stage 2: Provision Middleware

BASH 
.setup/setup-common.sh environment

Provisions the complete application runtime from scratch. This stage is fully automated and performs the following in sequence:

  1. Stops any existing Bank of Z tasks (CICS, IMS, z/OS Connect, frontend)
  2. Cleans up existing application datasets
  3. Clones the IBM DBB accelerators repository from GitHub
  4. Copies the zBuilder build framework
  5. Creates Db2 database tables
  6. Provisions a CICS region using zconfig
  7. Provisions an IMS region using zconfig
  8. Creates IMS database objects
  9. Starts IMS Bank of Z message processing regions
  10. Creates and starts a z/OS Connect server
  11. Creates and starts a frontend Liberty server

Note: This stage requires a pre-existing Db2 subsystem (DBD1). All other middleware, including CICS, IMS, z/OS Connect, and the frontend server, is provisioned automatically.

7.3 Stage 3: Build and Deploy

BASH 
.setup/setup-common.sh install-bank-of-z

Builds the application from source and deploys the generated artifacts to the provisioned runtime:

  1. Runs a full DBB build for all application sources, including COBOL, PL/I, Assembler, BMS, Java, and z/OS Connect APIs
  2. Packages the build outputs into a deployment archive
  3. Runs Wazi Deploy to deploy the archive to the CICS and IMS environments
  4. Populates Db2 with application test data
  5. Populates the IMS database with application test data

8. Verification

After any deployment method completes, verify the environment before proceeding with development activities.

8.1 Verification Checklist

Confirm the following components before proceeding:

  • [ ] Development tools are installed and accessible
  • [ ] Connectivity to the target z/OS environment is established
  • [ ] Required middleware components are available (CICS, IMS, Db2, z/OS Connect, IBM MQ)
  • [ ] Application artifacts have been deployed successfully
  • [ ] Runtime resources are active
  • [ ] Bank of Z services and APIs are operational

8.2 Verify Development Environment

Confirm that the required development tools are installed and accessible on your local machine.

Verify Java:

BASH 
java --version

Verify Git:

BASH 
git --version

Verify Zowe CLI:

BASH 
zowe --version

Verify z/OS connectivity:

BASH 
zowe zosmf check status

A successful response from zosmf check status confirms that the workstation can communicate with the target z/OS environment.

8.3 Verify Application Deployment

Confirm that the following application resources have been deployed successfully:

  • Application load modules are available
  • Db2 tables and plans have been created
  • IMS application resources are installed
  • CICS resources are active
  • z/OS Connect API artifacts have been deployed
  • Required configuration resources are available

8.4 Verify Application Access

Confirm that the application can process requests successfully by performing the following:

  • Accessing the Bank of Z user interface in a browser
  • Retrieving user information
  • Viewing account details
  • Executing account transactions
  • Invoking deployed z/OS Connect APIs

8.5 Run Post-Install Verification Tests (Direct USS)

If you deployed using Direct USS access, run the automated integration test suite:

BASH 
.setup/setup-common.sh verify-installation

This runs the tests in tests/ against the deployed application, exercises the CICS and IMS API paths, and reports a pass/fail result for each test. All tests must pass before the installation is considered complete.

9. Incremental Builds

After the initial deployment is complete, most day-to-day development can be performed using an incremental build and deploy instead of rebuilding the entire environment.

The incremental workflow rebuilds and deploys only the application components affected by your source code changes, reducing build time significantly while preserving the existing runtime environment.

graph TD A["✏️ Edit Source Files\n(COBOL, PL/I, Java, etc.)"] --> B{"Deployment\nWorkflow"} B -->|"Zowe CLI"| C["Run incremental\nZowe CLI workflow"] B -->|"GRUB"| D["Trigger GRUB sync\n(changed files only)"] C --> E["DBB Incremental Build\n(affected components only)"] D --> E E --> F["Package Changed Artifacts"] F --> G["Wazi Deploy\n(targeted deployment)"] G --> H["✅ Updated components\nlive in runtime"]

Incremental builds are significantly faster than a full deployment because DBB only recompiles the sources that have changed and their dependents. The runtime environment (CICS, IMS, Db2, z/OS Connect) remains running throughout the process.

For more information on day-to-day incremental development workflows, refer to the Zowe CLI Workflow and GRUB Workflow documentation.
