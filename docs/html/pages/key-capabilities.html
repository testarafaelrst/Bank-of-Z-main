Key Capabilities

Bank of Z demonstrates a combination of banking functionality and modern IBM Z development practices. The application serves as a realistic, open-source environment for learning, demonstrations, and experimentation with IBM Z technologies — bridging traditional enterprise systems with contemporary development workflows.

1. Overview

Bank of Z is a browser-based banking application built on IBM Z that integrates multiple transaction-processing systems into a unified user experience. It is designed to showcase how modern development practices can be applied to enterprise-grade mainframe applications without sacrificing reliability or performance.

The application supports real banking operations while simultaneously demonstrating how CICS and IMS Transaction Manager (IMS TM) can coexist in a hybrid architecture — sharing common banking data stored in Db2 for z/OS.

Bank of Z is intended for:

  • Learning IBM Z development workflows
  • Exploring application modernization approaches
  • Demonstrating enterprise application capabilities
  • Evaluating build and deployment automation
  • Experimenting with IBM Z development tools
  • Extending and customizing a sample banking application

2. System Architecture

Bank of Z is built around a hybrid architecture that routes customer requests through either CICS or IMS TM, depending on the selected implementation path. Both paths share a common data layer, ensuring consistency across all banking operations.

The diagram below illustrates the high-level system architecture and the relationships between the major components:

graph TD UI[Browser-Based UI] ZC[z/OS Connect] CICS[CICS Transaction Manager] IMS[IMS Transaction Manager - IMS TM] DB2[Db2 for z/OS] IMSDB[IMS DB] MQ[IBM MQ] UI --> ZC ZC --> CICS ZC --> IMS CICS --> DB2 IMS --> DB2 IMS --> IMSDB CICS --> MQ IMS --> MQ

The browser-based user interface communicates with the backend through z/OS Connect, which acts as the integration gateway. From there, requests are routed to either CICS or IMS TM. Both transaction managers interact with the shared Db2 for z/OS data layer, while IMS TM also has access to IMS DB. IBM MQ is available to both paths for message-based processing.

3. Banking Operations

Bank of Z supports a comprehensive set of standard banking operations. These operations are accessible through the browser-based interface and are processed by the underlying IBM Z transaction systems.

Supported operations include:

Operation Description
Account Management Create, view, and manage customer bank accounts
Customer Management Maintain customer profiles and associated data
Deposits Record deposit transactions against an account
Withdrawals Process withdrawal requests from an account
Funds Transfers Transfer funds between accounts
Transaction History Retrieve and display historical transaction records

The following sequence diagram illustrates a typical banking operation — in this case, a funds transfer — as it flows through the system:

sequenceDiagram actor User participant UI as Browser UI participant ZC as z/OS Connect participant TM as CICS or IMS TM participant DB as Db2 for z/OS participant MQ as IBM MQ User->>UI: Initiate funds transfer UI->>ZC: Submit transfer request (REST/API) ZC->>TM: Route to transaction manager TM->>DB: Debit source account TM->>DB: Credit destination account TM->>MQ: Post transaction event (optional) DB-->>TM: Confirmation TM-->>ZC: Transaction result ZC-->>UI: Response payload UI-->>User: Display confirmation

This flow applies consistently regardless of whether the CICS or IMS TM path is used, providing a transparent and uniform experience to the end user.

4. Hybrid Transaction Processing

One of the defining architectural features of Bank of Z is its hybrid transaction processing model. The application integrates both CICS and IMS Transaction Manager (IMS TM), allowing the user interface to route requests to either backend implementation while maintaining a consistent experience.

graph LR UI[Browser-Based UI] ZC[z/OS Connect API Gateway] CICS[CICS Path] IMS[IMS TM Path] DB2[(Db2 for z/OS - Shared Data)] UI -->|API Call| ZC ZC -->|Route A| CICS ZC -->|Route B| IMS CICS -->|Read / Write| DB2 IMS -->|Read / Write| DB2

Key characteristics of the hybrid model:

  • Dual transaction managers: Both CICS and IMS TM are supported as backend processors.
  • Shared data layer: Both paths read from and write to the same Db2 for z/OS database, ensuring data consistency.
  • Transparent routing: The user interface determines the processing path without exposing implementation details to the end user.
  • Consistent user experience: Regardless of which transaction manager handles the request, the response format and behavior remain uniform.

This design makes Bank of Z a practical reference for organizations that operate mixed CICS and IMS environments and need to demonstrate interoperability between them.

5. Modern Development Workflows

Bank of Z is built to reflect contemporary IBM Z development practices, making it a useful reference for teams modernizing their development pipelines. The project integrates several tools and workflows that align with modern software engineering standards.

5.1 Build Automation

The application uses Dependency Based Build (DBB) as its primary build framework:

GROOVY 
// Example: DBB build script invocation
dbb build --sourceDir ./src --buildFile application-conf/build.properties

DBB enables incremental builds by tracking source dependencies, reducing build times and ensuring only changed components are rebuilt.

Bob and zBuilder integration extends the build capabilities, providing additional flexibility in defining and executing build pipelines on z/OS.

5.2 Source Management

Bank of Z uses Git-based source management, enabling:

  • Branching and merging workflows familiar to modern development teams
  • Pull request-based code reviews
  • Integration with CI/CD pipelines
  • Version tracking across all COBOL, PL/I, and other z/OS source members

5.3 Development Environments

Developers can work with Bank of Z using two supported environments:

Environment Description
VS Code Develop z/OS applications locally using IBM Z extensions for VS Code
GRUB IBM Z-native development workflows using GRUB tooling

5.4 Automated Build and Deployment Pipelines

The project demonstrates end-to-end automation, from source commit to deployment on z/OS:

graph LR GIT[Git Repository] -->|Push / PR| CI[CI Pipeline] CI --> DBB[DBB Build] DBB --> PKG[Package Artifacts] PKG --> DEP[Deploy to z/OS] DEP --> CICS[CICS Region] DEP --> IMS[IMS Region]

This pipeline covers:

  • Triggering builds on code changes
  • Running dependency-based incremental builds
  • Packaging build outputs
  • Deploying to CICS and/or IMS regions on z/OS

6. Enterprise Integration

Bank of Z demonstrates deep integration across the IBM Z technology stack. The enterprise integration layer connects the browser-based frontend to multiple backend systems through a set of well-defined interfaces.

6.1 Integrated Technologies

Technology Role in Bank of Z
z/OS Connect RESTful API gateway bridging the web UI and z/OS backend services
CICS Transaction processing for the CICS implementation path
IMS TM Transaction processing for the IMS implementation path
Db2 for z/OS Relational database for shared banking data
IMS DB Hierarchical database used by the IMS processing path
IBM MQ Message queuing for asynchronous event processing

6.2 Integration Architecture

The diagram below shows how all integrated technologies relate to one another within the application:

graph TD Browser[Browser Client] ZC[z/OS Connect] CICS[CICS] IMSTM[IMS TM] DB2[(Db2 for z/OS)] IMSDB[(IMS DB)] MQ[IBM MQ] Browser -->|HTTPS / REST| ZC ZC -->|CICS Service| CICS ZC -->|IMS Service| IMSTM CICS -->|SQL| DB2 IMSTM -->|SQL| DB2 IMSTM -->|DL/I Calls| IMSDB CICS -->|Put / Get| MQ IMSTM -->|Put / Get| MQ

6.3 z/OS Connect as the API Gateway

z/OS Connect plays a central role in the Bank of Z integration story. It exposes CICS and IMS TM services as RESTful APIs, allowing the browser-based frontend to communicate with z/OS backends using standard HTTP/JSON protocols — without requiring changes to the underlying transaction programs.

This approach reflects a key modernization pattern: wrapping existing z/OS assets with modern APIs to enable integration with web, mobile, and cloud consumers.
