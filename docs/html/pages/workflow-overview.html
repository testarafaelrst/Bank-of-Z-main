Development Workflow Overview

Bank of Z supports modern, Git-based development practices for building, validating, and deploying changes to enterprise z/OS environments. This page provides an overview of the available development workflows and guidance on choosing the right approach for your development needs.

1. Overview

Bank of Z enables developers to modify application assets, build and validate changes, and deploy updates to the target z/OS environment. The platform supports enterprise z/OS technologies including:

  • Db2 – relational database management
  • CICS – transaction processing
  • IMS – hierarchical database and transaction management
  • z/OS Connect – API connectivity
  • IBM Dependency Based Build (DBB) – intelligent, dependency-aware build
  • Wazi Deploy – deployment automation

Two primary workflows are supported: the Zowe CLI workflow and the GRUB workflow. Both workflows prepare and update the same Bank of Z environment but differ in how source changes are synchronized and how development activities are performed.

2. System Architecture

The following diagram illustrates the high-level system architecture of Bank of Z and how the development workflows interact with the core platform components.

graph TD Dev[Developer Workstation] --> VCS[Git Repository / Source Control] Dev --> GRUB[GRUB Workflow] VCS --> ZoweCLI[Zowe CLI Workflow] ZoweCLI --> USS[z/OS USS - Clone & Setup] GRUB --> USS USS --> DBB[IBM Dependency Based Build - DBB] DBB --> Artifacts[Build Artifacts & Deployment Package] Artifacts --> WaziDeploy[Wazi Deploy] WaziDeploy --> CICS[CICS Runtime] WaziDeploy --> Db2[Db2 Database] WaziDeploy --> IMS[IMS Runtime] WaziDeploy --> zOSConnect[z/OS Connect APIs]

The developer workstation is the starting point for all changes. Depending on the chosen workflow, changes are either committed to Git and cloned via Zowe CLI, or synchronized directly to z/OS USS via GRUB. From USS, IBM DBB performs an intelligent, dependency-aware build, and the resulting artifacts are deployed to the target runtime environments through Wazi Deploy.

3. Development Workflow

A typical Bank of Z development cycle consists of the following sequential activities. While the specific tooling differs between workflows, the overall lifecycle remains consistent.

graph TD A[1. Make Changes] --> B[2. Commit Changes] B --> C[3. Run the Pipeline] C --> D[4. Review Results] D --> E{Issues Found?} E -- Yes --> A E -- No --> F[5. Deploy Changes] F --> G[6. Validate Changes] G --> H{Validation Passed?} H -- No --> A H -- Yes --> I[Promote to Next Environment]

Each step in the workflow is described in detail below.

3.1 Make Changes

Modify application source code, configuration files, or deployment artifacts. Common changes include:

  • COBOL programs
  • BMS maps
  • Copybooks
  • z/OS Connect API definitions
  • Web application components

3.2 Commit Changes

Review and commit changes to the source repository. Use meaningful commit messages to document modifications and support traceability.

Note: In the Zowe CLI workflow, commits are required before pipeline execution. In the GRUB workflow, commits are not required for daily development and testing activities.

3.3 Run the Pipeline

Run the build pipeline using the supported development workflow. The pipeline performs the following actions:

  • Analyzes source changes and their dependencies
  • Builds all affected components
  • Packages deployment artifacts
  • Prepares deployment plans

3.4 Review Results

Review build logs, reports, and generated artifacts. Address any build, dependency, or deployment issues identified during the pipeline run before proceeding.

3.5 Deploy Changes

Deploy validated artifacts to the target environment. Updated components are activated in the appropriate runtime environments, including CICS, Db2, IMS, and z/OS Connect.

3.6 Validate Changes

Verify that the deployed changes function as expected. Run application tests and review runtime behavior before promoting changes to additional environments.

4. Supported Workflows

Bank of Z supports two distinct development approaches, each suited to different development styles and access requirements.

4.1 Zowe CLI Workflow

A task-based workflow that uses Zowe CLI to clone your branch on z/OS USS and run the setup and pipeline scripts. This workflow integrates with VS Code and can be triggered from:

  • The command line
  • A VS Code task

This workflow is best suited for branch-based, version-controlled development where full Git integration and team collaboration are priorities.

BASH 
# Example: Trigger setup using the provided script
./setup-local.sh

4.2 GRUB Workflow

A development workflow optimized for rapid iteration. It allows you to synchronize changes directly to the target z/OS USS environment and run build and deployment activities without requiring committed changes first.

This workflow is best suited for fast, frequent, and incremental development cycles where rapid feedback is a priority.

sequenceDiagram participant Dev as Developer Workstation participant GRUB as GRUB Sync participant USS as z/OS USS participant DBB as IBM DBB participant Deploy as Wazi Deploy Dev->>GRUB: Save / modify source files GRUB->>USS: Synchronize changed files directly USS->>DBB: Trigger build pipeline DBB-->>USS: Build artifacts generated USS->>Deploy: Package and deploy changes Deploy-->>Dev: Deployment complete - validate results

The GRUB workflow eliminates the commit-before-test requirement, enabling a tighter inner-loop development cycle. Changes are synchronized directly to USS, and the setup is initiated automatically after synchronization.

5. Workflow Comparison

Both workflows ultimately prepare and update the same Bank of Z environment. Use the following comparison to determine which workflow best fits your development needs.

Feature Zowe CLI Workflow GRUB Workflow
Source synchronization Clones a Git repository branch on z/OS USS Synchronizes local changes directly to z/OS USS
Commit required before testing Yes No
GitHub dependency Required Not required for daily development
Remote access method Zowe CLI SSH and GRUB
Development style Branch-based and version-controlled Rapid local iteration
Change transfer Repository clone and setup execution Synchronization of changed files
Collaboration Well suited for shared branch-based development Primarily for individual development and testing
Setup execution VS Code task or setup-local.sh Initiated automatically after synchronization
Best suited for Feature development, team collaboration, restricted SSH access Fast testing, frequent code changes, rapid development cycles

5.1 When to Use the Zowe CLI Workflow

Use the Zowe CLI workflow when:

  • You work in a branch-based development model
  • Changes must be committed and tracked through Git
  • You want to use Zowe CLI and VS Code integration
  • SSH access to z/OS USS is limited or unavailable

5.2 When to Use the GRUB Workflow

Use the GRUB workflow when:

  • You need to test changes quickly without committing them first
  • You want rapid feedback during active development
  • You have direct SSH access to z/OS USS
  • You frequently make and validate incremental changes

6. Choosing the Right Workflow

The decision tree below summarizes how to choose the appropriate workflow based on your development context.

graph TD Start([Start]) --> Q1{Do you have SSH access\nto z/OS USS?} Q1 -- No --> ZoweCLI[Use Zowe CLI Workflow] Q1 -- Yes --> Q2{Do you need to commit\nbefore testing?} Q2 -- Yes --> ZoweCLI Q2 -- No --> Q3{Is rapid iteration\nyour priority?} Q3 -- Yes --> GRUB[Use GRUB Workflow] Q3 -- No --> Q4{Are you collaborating\non a shared branch?} Q4 -- Yes --> ZoweCLI Q4 -- No --> GRUB

Both workflows are fully supported and lead to the same outcome: a built, deployed, and validated Bank of Z environment. Your choice should be driven by your access requirements, collaboration needs, and preferred development cadence.
