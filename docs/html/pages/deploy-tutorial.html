Tutorial: Deploy Bank of Z

This tutorial walks you through a complete first-time deployment of the Bank of Z application on IBM Z. You will use the Direct USS method to clone the repository, run the three setup stages, and bring up a full application stack — including CICS, IMS, z/OS Connect, and a Liberty frontend server — then build and deploy the application from source.

1. Overview

Bank of Z is a full-stack banking sample application designed for IBM Z environments. It demonstrates hybrid cloud development and modernization workflows by combining traditional mainframe components (CICS, IMS) with modern runtimes (z/OS Connect, Liberty). The deployment covered in this tutorial provisions all of these components automatically through a series of scripted setup stages.

This tutorial is the first in a series. Subsequent tutorials build on this deployment to explore enhancement and debugging scenarios.

By completing this tutorial, you will learn how to:

  • Clone the Bank of Z repository to USS (Unix System Services)
  • Execute the three automated setup stages
  • Provision a full IBM Z application stack from source
  • Understand the incremental build and deploy workflow for day-to-day development

Tip: Once Bank of Z has been deployed successfully, use the incremental build and deploy workflow (pipeline-remote.sh) during day-to-day development instead of performing a full deployment after every code change.

2. System Architecture

The Bank of Z application stack spans several IBM Z middleware components. The diagram below illustrates how the layers relate to one another, from the user-facing frontend down to the backend transaction and database runtimes.

graph TD A[User / Browser] --> B[Liberty Frontend Server] B --> C[z/OS Connect] C --> D[CICS Transaction Server] C --> E[IMS Transaction Manager] D --> F[VSAM / Application Data] E --> G[IMS Database] B --> H[USS - Unix System Services] H --> I[Repository Source Code] I --> J[Build & Deploy Pipeline] J --> D J --> E J --> B

The Liberty frontend server acts as the entry point for browser-based requests. z/OS Connect serves as the integration layer, routing API calls to the appropriate backend — either CICS or IMS — depending on the transaction type. All components are provisioned and deployed directly from source code residing on USS.

3. Prerequisites

Before beginning this tutorial, ensure your z/OS environment meets all requirements described in the Deploying Bank of Z documentation. At a high level, the following must be in place:

  • A z/OS system with USS enabled
  • Access credentials with sufficient authority to provision CICS, IMS, and Liberty resources
  • Git available on USS for cloning the repository
  • All prerequisite software installed and configured (Java, CICS TS, IMS, z/OS Connect)

4. Deployment Walkthrough

4.1 Overview of the Deployment Flow

The full first-time deployment follows a linear sequence: clone the source, run three setup stages, and verify the running application. The sequence diagram below captures this end-to-end flow.

sequenceDiagram actor Developer participant USS as USS Shell participant Repo as GitHub Repository participant Stage1 as Setup Stage 1 participant Stage2 as Setup Stage 2 participant Stage3 as Setup Stage 3 participant Stack as Application Stack Developer->>USS: SSH into z/OS USS environment Developer->>USS: git clone USS->>Repo: Fetch Bank of Z source code Repo-->>USS: Repository cloned to USS Developer->>Stage1: Run Stage 1 script Stage1-->>Stack: Provision CICS & IMS environments Developer->>Stage2: Run Stage 2 script Stage2-->>Stack: Configure z/OS Connect & Liberty Developer->>Stage3: Run Stage 3 script Stage3-->>Stack: Build & deploy application from source Stack-->>Developer: Bank of Z application running

Each stage is automated and builds on the previous one. You do not need to manually configure individual middleware components — the scripts handle provisioning end to end.

4.2 Stage 1 — Provision the Backend Environment

The first setup stage provisions the CICS and IMS runtime environments. This includes creating the necessary CICS regions, IMS subsystems, and the supporting z/OS resources required by the application.

Run the Stage 1 script from the cloned repository directory on USS:

BASH 
./setup-stage1.sh

Monitor the output for any provisioning errors before proceeding to Stage 2.

4.3 Stage 2 — Configure z/OS Connect and Liberty

The second stage configures z/OS Connect as the API integration layer and sets up the Liberty frontend server. After this stage completes, the middleware routing infrastructure is in place.

BASH 
./setup-stage2.sh

4.4 Stage 3 — Build and Deploy the Application

The third and final setup stage compiles the application source code and deploys all artifacts to the provisioned stack. This includes the COBOL programs deployed to CICS and IMS, the z/OS Connect API definitions, and the Liberty web application.

BASH 
./setup-stage3.sh

Once this stage completes successfully, the full Bank of Z application stack is running and accessible.

6. Day-to-Day Development Workflow

After completing the initial full deployment, you do not need to repeat all three stages for every code change. Bank of Z provides an incremental build and deploy workflow designed for iterative development.

6.1 Incremental Build and Deploy

Use the pipeline-remote.sh script to build and deploy only the components that have changed. This significantly reduces the time between making a code change and seeing it reflected in the running application.

BASH 
./pipeline-remote.sh

The diagram below contrasts the full deployment path with the incremental workflow:

graph TD A[Code Change] --> B{First-Time Deployment?} B -- Yes --> C[Stage 1: Provision CICS & IMS] C --> D[Stage 2: Configure z/OS Connect & Liberty] D --> E[Stage 3: Build & Deploy from Source] E --> F[Application Running] B -- No --> G[Run pipeline-remote.sh] G --> H[Incremental Build & Deploy] H --> F
