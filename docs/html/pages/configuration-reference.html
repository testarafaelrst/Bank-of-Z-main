Configuration Reference

Bank of Z uses the .setup/config/config.yaml file to define all environment-specific settings used during setup, build, and deployment. This reference document describes every configuration parameter available, including required and optional settings, variable expansion rules, validation constraints, and environment-specific examples. The configuration file is written in YAML format and supports hierarchical organization, variable expansion, and environment variable references.

1. Overview

The Bank of Z configuration system is driven by a single YAML file located at .setup/config/config.yaml. This file is the authoritative source for all paths, middleware settings, application identifiers, and infrastructure references consumed by setup scripts, build tools, and deployment automation.

The configuration file supports the following features:

  • Hierarchical configuration using YAML sections for logical grouping of related settings
  • Variable expansion using {{ section.key }} syntax for referencing values within the file
  • Environment variable references using ${ENV_VAR} syntax for injecting runtime or sensitive values
  • Comments using the # character for inline documentation

Below is a minimal example illustrating these features together:

YAML 
# Global properties
global:
  sandbox_root: "/usr/local/sandboxes"
  app_base_name: "BANKZ"
  app_hlq: "{{ global.app_base_name }}"       # Variable expansion
  zos_current_user: "${ZOS_CURRENT_USER}"      # Environment variable reference
  db2_sqlid: "{{ global.zos_current_user }}"  # Chained variable reference

2. System Architecture

Bank of Z is a mainframe-native application that spans multiple middleware layers on z/OS. The configuration file defines how each of these layers is located, connected, and identified. Understanding the overall architecture helps clarify why certain configuration sections are required and how they relate to one another.

The following diagram illustrates the high-level system architecture and the configuration sections that govern each component:

graph TD A[config.yaml] --> B[global section] B --> C[Sandbox & Application Identity] B --> D[z/OS System Settings] B --> E[Tool Paths] B --> F[Middleware Configuration] F --> G[CICS Region] F --> H[IMS Datastore] F --> I[DB2 Subsystem] F --> J[z/OS Connect GUI Layer] F --> K[Liberty Frontend] E --> L[DBB - Dependency Based Build] E --> M[Wazi Deploy] E --> N[ZCodeScan] E --> O[zConfig / CRB] E --> P[Gradle / Java / Python / ZOAU] C --> Q[Dataset HLQ: BANKZ.V0R1M0.*] D --> R[RACF: Keyring / CA / Users]

The diagram above shows how config.yaml acts as the single source of truth feeding into all layers of the deployment. The global section drives everything from dataset naming conventions to middleware port assignments.

The following diagram shows how configuration values flow through the setup and deployment pipeline:

sequenceDiagram participant Dev as Developer participant Cfg as config.yaml participant Setup as Setup Scripts participant zOS as z/OS Environment participant MW as Middleware (CICS/IMS/DB2) Dev->>Cfg: Edit global section values Dev->>Setup: Run setup script Setup->>Cfg: Read and validate config.yaml Cfg-->>Setup: Resolved configuration values Setup->>zOS: Apply system settings (RACF, datasets, USS paths) Setup->>MW: Configure CICS regions, IMS datastores, DB2 subsystem MW-->>zOS: Middleware ready zOS-->>Dev: Deployment complete

3. Required Settings

The global section is the primary configuration block. All settings within it are shared across setup scripts, middleware configurations, and supporting tools. The subsections below document each parameter group in detail.

3.1 Sandbox

The sandbox_root parameter defines the root directory on z/OS UNIX System Services (USS) where all Bank of Z components are installed. It must be an absolute path, the user must have write permissions, and the parent directory must already exist.

Variable Default Value Description
sandbox_root /usr/local/sandboxes Root directory of the sandbox
YAML 
global:
  sandbox_root: "/usr/local/sandboxes"

Environment-specific examples:

YAML 
# Development environment
global:
  sandbox_root: "/usr/local/sandboxes/dev"

# Test environment
global:
  sandbox_root: "/usr/local/sandboxes/test"

# Personal sandbox
global:
  sandbox_root: "/u/userid/sandboxes"

3.2 Application

The app parameters define naming conventions used for datasets, CICS resources, and deployment artifacts. These identifiers must conform to z/OS dataset naming rules and character length limits.

Variable Default Value Description
app_base_name BANKZ Application base name (dataset HLQ, max 8 characters)
app_hlq {{ global.app_base_name }} Application high-level qualifier
app_short_name BOZ Application short name (max 3 characters)
app_version 0 Application version number
app_release 1 Application release number
app_modification 0 Application modification level
YAML 
global:
  app_base_name: "BANKZ"
  app_hlq: "{{ global.app_base_name }}"
  app_short_name: "BOZ"
  app_version: "0"
  app_release: "1"
  app_modification: "0"

These values combine to form dataset names in the pattern BANKZ.V0R1M0.LOAD, where the version string is derived from app_version, app_release, and app_modification.

Examples for different environments:

YAML 
# Development version
global:
  app_base_name: "BANKZD"
  app_short_name: "BOZ"
  app_version: "0"
  app_release: "1"
  app_modification: "0"

# Production version
global:
  app_base_name: "BANKZP"
  app_short_name: "BOZ"
  app_version: "1"
  app_release: "0"
  app_modification: "0"

python_home /usr/lpp/IBM/cyp/v3r14/pyz Python installation path
zoau_home /usr/lpp/IBM/zoau ZOAU installation path
zconfig_home {{ global.sandbox_root }}/tools/zconfig zconfig installation path
zcb_home {{ global.sandbox_root }}/tools/zrb/cics-resource-builder-1.0.6 CICS Resource Builder installation path

zosconnect_home /usr/lpp/IBM/zosconnect z/OS Connect installation path
liberty_home /usr/lpp/liberty_zos/25.0.0.9 Liberty installation path

3.5 GUI (z/OS Connect)

The GUI parameters configure the z/OS Connect instance that exposes backend services to the frontend application. Both HTTP and HTTPS ports must be available and not blocked by your network security configuration.

Variable Default Value Description
zosconnect_http_port 9080 z/OS Connect HTTP port
zosconnect_https_port 9444 z/OS Connect HTTPS port
zosconnect_task_user {{ global.zos_admin_user }} z/OS Connect task user
YAML 
global:
  zosconnect_http_port: 9080
  zosconnect_https_port: 9444
  zosconnect_task_user: "{{ global.zos_admin_user }}"

3.6 Frontend (Liberty)

The frontend parameters configure the Liberty server that hosts the Bank of Z web application.

Variable Default Value Description
frontend_http_port 9081 Frontend HTTP port
frontend_https_port 9445 Frontend HTTPS port
frontend_task_user {{ global.zos_admin_user }} Frontend task user
YAML 
global:
  frontend_http_port: 9081
  frontend_https_port: 9445
  frontend_task_user: "{{ global.zos_admin_user }}"

3.7 CICS

The CICS parameters identify the CICS Transaction Server installation and control security enforcement for CICS regions used by Bank of Z.

Variable Default Value Description
cics_hlq CICSTS63 CICS high-level qualifier
cics_uss_dir /usr/lpp/cicsts/cicsts63 CICS USS directory
cics_sec YES CICS security enabled flag
YAML 
global:
  cics_hlq: "CICSTS63"
  cics_uss_dir: "/usr/lpp/cicsts/cicsts63"
  cics_sec: "YES"

3.8 IMS

The IMS parameters configure the IMS database subsystem used by the Bank of Z backend. IMS can be disabled for environments where only DB2 is used.

Variable Default Value Description
ims_disabled false Set to true to disable IMS integration
ims_sys_hlq IMSV15 IMS system high-level qualifier
ims_java_dir /usr/lpp/ims/imsjava IMS Java installation path
ims_datastore IMS2 IMS datastore name
ims_dfsplex PLEX2 IMS DFSPLEX name
YAML 
global:
  ims_disabled: "false"
  ims_sys_hlq: "IMSV15"
  ims_java_dir: "/usr/lpp/ims/imsjava"
  ims_datastore: "IMS2"
  ims_dfsplex: "PLEX2"

3.9 DB2

The DB2 parameters identify the Db2 subsystem and control how the setup scripts connect to and configure the database layer. The db2_grants list specifies which user IDs should be granted access to Bank of Z Db2 objects.

Variable Default Value Description
db2_hlq DB2V13 DB2 high-level qualifier
db2_dsntep DSNTEP13 DB2 DSNTEP program name
db2_ssid DBD1 DB2 subsystem ID
db2_runlib {{ global.db2_ssid }}.RUNLIB.LOAD DB2 RUNLIB dataset
db2_sqlid {{ global.zos_current_user }} DB2 SQL ID
db2_java_dir /usr/lpp/db2d10 DB2 Java installation path
db2_grants CICSUSER List of DB2 grantees
YAML 
global:
  db2_hlq: "DB2V13"
  db2_dsntep: "DSNTEP13"
  db2_ssid: "DBD1"
  db2_runlib: "{{ global.db2_ssid }}.RUNLIB.LOAD"
  db2_sqlid: "{{ global.zos_current_user }}"
  db2_java_dir: "/usr/lpp/db2d10"
  db2_grants:
    - "CICSUSER"

4. Optional Configuration Sections

Beyond the global section, additional named sections can be defined to configure specific tools and subsystems. These sections are only required when the corresponding tooling or capability is enabled in your deployment.

The following diagram illustrates the relationship between optional configuration sections and the deployment pipeline stages they support:

graph LR A[config.yaml Optional Sections] --> B[repositories] A --> C[zbuilder] A --> D[zconfig] A --> E[zcodescan] A --> F[wazideploy] A --> G[taz] A --> H[cics credentials] B --> I[Git Clone Stage] C --> J[Build Stage] D --> J E --> K[Scan Stage] F --> L[Deploy Stage] G --> M[Test Stage] H --> L

4.1 Repository Configuration

Defines the Git repositories that are cloned during setup. Each entry specifies a repository name, its clone URL, and the target directory within the workspace.

YAML 
repositories:
  - name: dbb
    url: https://github.com/IBM/dbb.git
    target_dir: dbb
  - name: custom-tools
    url: https://github.com/company/tools.git
    target_dir: tools

Fields:

Field Description
name Repository identifier used in logs and scripts
url Git clone URL (HTTPS or SSH)
target_dir Directory name within the workspace

4.2 zBuilder Configuration

Defines where the zBuilder source and deployment artifacts are located. zBuilder is the framework used to manage build pipelines and dataset definitions.

YAML 
zbuilder:
  source_dir: build
  target_dir: "${sandbox.path}/zBuilder"
  java_home: "/usr/lpp/java/java21/current_64"

Fields:

Field Description
source_dir Local directory containing zBuilder framework, relative to .setup/
target_dir USS directory where zBuilder is deployed (supports variable expansion)
java_home Java runtime for zBuilder (minimum Java 17)

4.3 zconfig Configuration

Defines settings for z/OS configuration tooling, including the CICS Resource Builder (CRB). Required when using automated CICS resource provisioning.

YAML 
zconfig:
  zconfig_home: "/usr/local/sandboxes/tools/zconfig"
  zcb_home: "/usr/local/sandboxes/tools/zrb/cics-resource-builder-1.0.6"
  java_home: "/usr/lpp/java/java21/current_64"

4.4 ZCodeScan Configuration

Defines settings used for static code analysis. The ZCodeScan configuration file must be encoded in ISO8859-1 and is referenced here by path.

YAML 
zcodescan:
  zcodescan_home: "/global/opt/pyenv/akf"
  java_home: "/usr/lpp/java/java21/current_64"
  src_folder: "${sandbox.path}/Bank-of-Z/src/base"
  output_folder: "${sandbox.path}/Bank-of-Z/zcodescan"
  src_encoding: "IBM-1047"
  rseapi_user: "${RESAPI_USER}"
  rseapi_password: "${RESAPI_PASSWORD}"

The ZCodeScan license configuration file must be created separately and saved in ISO8859-1 encoding:

YAML 
# ~/zcs_config_file.yml (encoded in ISO8859-1)
license_server:
  url: https://127.0.0.1:8195
  user: MYUSER
  password: MY_PASSWORD
  verify: false

Note: The password is automatically encrypted after the first scan. Provide it in plain text only on first use.

4.5 Wazi Deploy Configuration

Defines deployment automation settings used by Wazi Deploy to manage package deployment to z/OS environments.

YAML 
wazideploy:
  wazideploy_home: "/global/opt/pyenv/gdp"
  deployment_method: "${sandbox.path}/dbb/WaziDeploy/zDeploy/deployment-configuration/deployment-method.yml"
  deployment_envfile: "${sandbox.path}/Bank-of-Z/.setup/deploy/Development.yml"

4.6 TAZ Unit Test Configuration

Defines settings for automated unit testing using the TAZ test framework. Required when running automated test suites as part of the pipeline.

YAML 
taz:
  taz_home: "/usr/local/sandboxes/tools/taz-280/test-cli"
  test_folder: "${sandbox.path}/Bank-of-Z/tests"
  proclib: "SYS1.PROCLIB"
  library: "${app.base_name}.${app.zos_version}.LOAD"

4.7 CICS Credentials

Provides connection details for the CICS region used during deployment and automation tasks. Using environment variables for credentials is strongly recommended.

YAML 
# Recommended: use environment variables for sensitive values
cics:
  user: "${CICS_USER}"
  password: "${CICS_PASSWORD}"
  cmci_port: 27100
  ipic_port: 27114

Similarly, IMS credentials must be exported as environment variables before running setup:

BASH 
export IMS_USER=<your_ims_user>
export IMS_PASSWORD=<your_ims_password>

export CICS_USER=<your_cics_user>
export CICS_PASSWORD=<your_cics_password>

5. Variable Expansion

Variable expansion allows configuration values to reference other values defined elsewhere in config.yaml or in the runtime environment. This avoids duplication and ensures consistency across related settings.

5.1 Section References

Use the {{ section.key }} syntax to reference a value from within the configuration file itself.

YAML 
global:
  sandbox_root: "/usr/local/sandboxes"
  dbb_home: "{{ global.sandbox_root }}/tools/dbb"
  gradle_home: "{{ global.sandbox_root }}/tools/gradle-9.5.1"

Resolution is recursive, meaning a variable can reference another variable that itself uses variable expansion:

YAML 
global:
  db2_ssid: "DBD1"
  db2_runlib: "{{ global.db2_ssid }}.RUNLIB.LOAD"
  db2_sqlid: "{{ global.zos_current_user }}"
  zos_current_user: "${ZOS_CURRENT_USER}"

5.2 Environment Variable References

Use ${ENV_VAR} syntax to inject values from the shell environment. This pattern is required for sensitive information such as credentials and user identities:

YAML 
global:
  zos_current_user: "${ZOS_CURRENT_USER}"

cics:
  user: "${CICS_USER}"
  password: "${CICS_PASSWORD}"

zcodescan:
  rseapi_user: "${RESAPI_USER}"
  rseapi_password: "${RESAPI_PASSWORD}"

Note: The referenced environment variable must be exported in the shell before running setup scripts, otherwise variable resolution will fail.

7. Validation Rules

Before any setup script runs, the configuration file is validated to ensure all required fields are present, all references can be resolved, and all values conform to z/OS naming and path constraints. Correcting configuration issues before running setup prevents build and deployment failures.

The following diagram shows the validation flow:

graph TD A[Load config.yaml] --> B{Required fields present?} B -- No --> Z1[Error: Missing required field] B -- Yes --> C{All variable references resolvable?} C -- No --> Z2[Error: Unresolved variable reference] C -- Yes --> D{All paths are absolute?} D -- No --> Z3[Error: Invalid path format] D -- Yes --> E{Character limits respected?} E -- No --> Z4[Error: Name too long] E -- Yes --> F{Tool locations defined?} F -- No --> Z5[Warning: Optional tool not configured] F -- Yes --> G[Validation Passed - Proceed with Setup]

7.1 Required Fields

The following fields must be present and non-empty in config.yaml:

Field Section Constraint
sandbox_root global Must be an absolute path
app_base_name global Maximum 8 characters, alphanumeric
app_short_name global Maximum 3 characters
dbb_home global Must point to a valid DBB installation
java_home global Must point to Java 8 or higher

7.2 Path Format Rules

  • All paths must be absolute (begin with /)
  • No trailing slashes
  • Paths must reference existing directories at setup time

7.3 Variable Resolution Rules

  • All {{ section.key }} references must resolve to a defined key
  • All ${ENV_VAR} references must correspond to an exported environment variable
  • Circular references are not permitted

7.4 Character Limits

Field Maximum Length Used In
app_base_name 8 characters Dataset HLQ
app_short_name 3 characters CICS region names, transaction IDs

8. Troubleshooting

8.1 Configuration File Not Found

Symptom: Setup script reports that config.yaml is missing.

Resolution: Verify the file exists at the correct path and that you are running the script from the repository root:

BASH 
# Verify the file exists
ls -la .setup/config/config.yaml

# Confirm the working directory
pwd

8.2 Variable Reference Cannot Be Resolved

Symptom: Setup fails with an error indicating an unresolved variable.

Cause: A {{ section.key }} reference points to a section or key that does not exist.

Resolution: Ensure the referenced section and key match exactly:

YAML 
# Incorrect: references a non-existent section name
dbb:
  build_dir: "${workspace.path}/build"   # 'workspace' does not exist

# Correct: uses the defined section name
dbb:
  build_dir: "${sandbox.path}/build"

8.3 Invalid Path Format

Symptom: Validation reports an invalid path.

Cause: A path value is relative rather than absolute.

Resolution: Ensure all path values start with /:

YAML 
# Incorrect: relative path
global:
  sandbox_root: "sandboxes/bank-of-z"

# Correct: absolute path
global:
  sandbox_root: "/usr/local/sandboxes/bank-of-z"

8.4 Environment Variable Not Set

Symptom: Setup fails with an unresolved ${ENV_VAR} reference.

Cause: The required environment variable was not exported before running setup.

Resolution: Export the variable in your shell session:

BASH 
export ZOS_CURRENT_USER=myuserid
export CICS_USER=myuserid
export CICS_PASSWORD=mypassword
export IMS_USER=myuserid
export IMS_PASSWORD=mypassword
