Zowe CLI Workflow

The Zowe CLI workflow enables Git-based development for the Bank of Z application, allowing developers to build and deploy changes from a local workstation to z/OS USS without requiring direct SSH access. By using setup-local.sh and pipeline-local.sh, the workflow coordinates all build and deployment activities between your local machine and z/OS USS, cloning your branch from GitHub and executing remote setup commands automatically.

Before using this workflow, ensure your environment is fully configured by completing the Zowe CLI Setup and Zowe Profile Setup steps.

1. System Architecture

The Zowe CLI workflow bridges your local development environment and z/OS USS through a layered set of tools and scripts. Zowe CLI, backed by the IBM RSE API plug-in, acts as the communication layer between the developer’s workstation and the remote z/OS system. The diagram below illustrates how the components relate to one another.

graph TD A[Developer Workstation] --> B[Zowe CLI] B --> C[IBM RSE API Plug-in] C --> D[z/OS USS] A --> E[GitHub Repository] E --> D D --> F[DBB Build] D --> G[Wazi Deploy] F --> H[CICS / Bank of Z Application] G --> H B --> I[zosmf API] I --> D subgraph Local Machine A end subgraph z/OS D F G H end

Zowe CLI communicates with z/OS through two channels: the IBM RSE API plug-in for USS file and command operations, and the z/OSMF API for broader z/OS interactions. The remote USS environment pulls source code directly from GitHub, ensuring that only committed and pushed changes are built and deployed.

2. Overview

2.1 What the Workflow Does

The Zowe CLI workflow automates the following sequence of operations every time a build is triggered:

  1. Creates or validates a USS workspace directory on the target z/OS system.
  2. Clones the developer’s current branch from GitHub into that workspace.
  3. Invokes remote setup or pipeline scripts natively on USS.
  4. Runs a DBB build and Wazi Deploy to compile and deploy the Bank of Z application.

2.2 Full vs. Incremental Builds

Bank of Z supports both full and incremental build workflows:

Build Type When to Use Script
Full Build First-time setup or after infrastructure changes setup-local.sh
Incremental Build Day-to-day development after initial deployment pipeline-local.sh

An incremental build rebuilds and deploys only the application components affected by your changes, making it significantly faster for routine development iterations.

2.3 Performance Comparison

Operation Zowe CLI GRUB
Initial setup ~5–8 minutes ~3–6 minutes
Incremental update ~5–8 minutes ~5–10 seconds
Requires push to remote Yes No

Note: Because the Zowe CLI workflow clones your branch from GitHub on USS, all changes must be committed and pushed before triggering a build. Unpushed commits will not be included.

3. Prerequisites

Before using the Zowe CLI workflow, ensure the following tools and configurations are in place.

3.1 Node.js and npm

Verify that the correct versions of Node.js and npm are installed:

BASH 
node -v   # Required: >=22.22.1 <23
npm -v    # Required: >=10.9.4 <10.10.0

3.2 Install Zowe CLI

Install the Zowe CLI globally via npm:

BASH 
npm install -g @zowe/cli@zowe-v3-lts

Verify the installation:

BASH 
zowe --version

3.3 Install the IBM RSE API Plug-in

The IBM RSE API plug-in is required for setup-local.sh to run USS commands and manage files on the target z/OS system:

BASH 
zowe plugins install @ibm/rse-api-for-zowe-cli

Verify that the plug-in is installed:

BASH 
zowe plugins list

3.4 Configure a Zowe Profile

A Zowe profile stores the connection details used by Zowe CLI to communicate with your z/OS system. Create ~/.zowe/zowe.config.json with the following content, updating the fields marked for your environment:

  • host — Host name or IP address of your z/OS system.
  • account — Your TSO account number.
  • logonProcedure — Your TSO logon procedure.
  • Ports — Update these values if your environment uses non-default ports.
JSON 
{
  "$schema": "./zowe.schema.json",
  "profiles": {
    "BankOfZDemo": {
      "properties": {
        "host": "<your host>",
        "rejectUnauthorized": false
      },
      "secure": ["user", "password"],
      "profiles": {
        "rseapi": {
          "type": "rse",
          "properties": {
            "port": 8195,
            "basePath": "rseapi",
            "protocol": "https"
          }
        },
        "zosmf": {
          "type": "zosmf",
          "properties": {
            "port": 10443
          }
        },
        "ssh": {
          "type": "ssh",
          "properties": {
            "port": 22
          }
        },
        "tso": {
          "type": "tso",
          "properties": {
            "account": "<account>",
            "codePage": "1047",
            "logonProcedure": "<logon procedure>"
          }
        },
        "zOpenDebug": {
          "type": "zOpenDebug",
          "properties": {
            "dpsPort": 8192,
            "rdsPort": 8194,
            "dpsContextRoot": "api/v1",
            "dpsSecured": true,
            "authenticationType": "basic",
            "uuid": "4267a0f6-b756-4f3c-b900-0b959b4567c3"
          }
        }
      }
    }
  },
  "defaults": {
    "zosmf": "BankOfZDemo.zosmf",
    "tso": "BankOfZDemo.tso",
    "ssh": "BankOfZDemo.ssh",
    "rse": "BankOfZDemo.rseapi",
    "zOpenDebug": "BankOfZDemo.zOpenDebug"
  },
  "autoStore": true
}

3.5 Verify Connectivity

Verify that Zowe CLI can connect to your z/OS system using your configured profile:

BASH 
zowe zosmf check status
zowe rse check status

If the connection fails, verify that the host, ports, and credentials are correct and that the corresponding services are running on z/OS.

4. Daily Development Cycle

The following sections describe the standard day-to-day development cycle when using the Zowe CLI workflow. The sequence diagram below shows the end-to-end flow from making a local change to validating it in the running application.

sequenceDiagram participant Dev as Developer participant Git as GitHub Repository participant Local as Local Machine participant ZOSS as z/OS USS participant App as Bank of Z App Dev->>Local: Modify source code Dev->>Git: git add / commit / push Dev->>Local: Run setup-local.sh or pipeline-local.sh Local->>ZOSS: Create USS workspace directory ZOSS->>Git: git clone (developer's branch) Local->>ZOSS: Invoke setup-remote.sh / pipeline-remote.sh ZOSS->>ZOSS: validate-prereqs ZOSS->>ZOSS: DBB Build ZOSS->>ZOSS: Wazi Deploy ZOSS->>App: Deploy compiled artifacts Dev->>App: Validate changes in browser

4.1 Make Changes

Modify application source code in your local workspace. Common changes include:

  • COBOL programs and copybooks
  • BMS maps
  • z/OS Connect API assets
  • Web application components
  • Configuration files

4.2 Commit and Push

All changes must be pushed to the remote repository before triggering a build. The script clones your branch from GitHub on USS, so any unpushed commits will not be included in the build.

BASH 
git add .
git commit -m "Your change description"
git push origin your-branch

4.3 Run the Setup or Pipeline Task

You can trigger the build either from the command line or from within VS Code.

From the command line:

BASH 
# Full environment setup (first time or after infrastructure changes)
bash .setup/setup-local.sh

# Incremental build and deploy only
bash .setup/pipeline-local.sh

From VS Code: Open the Command Palette and select Tasks: Run Task, then choose the appropriate task.

The VS Code task is defined in .vscode/tasks.json:

JSON 
{
  "version": "2.0.0",
  "tasks": [
    {
      "label": "Setup Bank of Z Environment",
      "type": "shell",
      "command": "bash .setup/setup-local.sh",
      "problemMatcher": [],
      "presentation": {
        "reveal": "always",
        "panel": "new"
      }
    }
  ]
}

4.4 What Runs Automatically

Once triggered, the scripts coordinate all activity between your local machine and z/OS USS without requiring manual intervention. The following diagram illustrates what each script does and where it runs:

graph TD A[setup-local.sh on Local Machine] --> B[Create USS Workspace Directory] A --> C[Clone Branch from GitHub onto USS] A --> D[Invoke setup-remote.sh on USS] D --> E[validate-prereqs] D --> F[environment provisioning] D --> G[install-bank-of-z] H[pipeline-local.sh on Local Machine] --> I[Upload Pipeline Assets to USS] H --> J[Invoke pipeline-remote.sh on USS] J --> K[DBB Build] J --> L[Wazi Deploy] K --> M[Bank of Z Application] L --> M

For incremental builds, pipeline-local.sh uploads pipeline assets and invokes pipeline-remote.sh on USS, which runs the DBB build and Wazi Deploy without re-provisioning middleware — keeping build times fast.

For full builds, setup-local.sh provisions the complete environment, including middleware and all application components.

4.5 Validate Changes

Once deployment completes, open the Bank of Z frontend in a browser to verify your changes are live:

CODE 
http://<your-zos-host>:9080/bank-frontend-vanilla

5. Working with Branches

The script automatically detects your current local branch and uses it when cloning on USS. To work on a feature branch:

BASH 
# Switch to your feature branch before running
git checkout feature/my-change
git push origin feature/my-change
bash .setup/setup-local.sh

Each developer can use a separate workspace path in config.yaml to avoid conflicts on USS when multiple developers are working on the same system simultaneously.
