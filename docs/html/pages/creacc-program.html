CREACC - Create Account Program

1. Overview

CREACC is a CICS-hosted COBOL program that implements the bank account creation transaction for the Bank of Z core banking system. It serves as the authoritative account provisioning service, responsible for atomically validating a customer, sequencing a new account number, persisting the account record to DB2, and writing an immutable audit trail to the processed transaction store — all within a single CICS task execution.

The program receives account creation details through the CICS COMMAREA, including customer number, account type, interest rate, overdraft limit, and opening balances. It then performs a series of sequential validations before acquiring an exclusive resource lock, generating the next sequential account number, inserting the account into DB2, and recording the event in the processed transaction audit table.

The program’s inline comment precisely captures its mandate:

“Enqueue the Named Counter for ACCOUNT, increment the counter and take the new account number, & attempt to update the ACCOUNT datastore on DB2. If that is successful, write a rec to the PROCTRAN datastore.”

Any failure at any stage sets the COMMAREA success flag to 'N' along with a specific single-character failure code and causes the program to return immediately, with the NCS resource dequeued where appropriate to preserve sequence integrity.

3. Inputs

3.1 Communication Area (DFHCOMMAREA) — Caller-Supplied Inputs

Field Description
COMM-CUSTNO The customer number provided by the calling program. Used to validate customer existence and populate the DB2 ACCOUNT table
COMM-ACC-TYPE The requested account type (e.g., ISA, MORTGAGE, SAVING, CURRENT, LOAN). Validated by the ACCOUNT-TYPE-CHECK paragraph
COMM-INT-RT The interest rate for the new account. Mapped to HV-ACCOUNT-INT-RATE and inserted into ACCOUNT_INTEREST_RATE
COMM-OVERDR-LIM The overdraft limit for the new account. Mapped to HV-ACCOUNT-OVERDRAFT-LIM
COMM-AVAIL-BAL The initial available balance for the new account
COMM-ACT-BAL The initial actual (ledger) balance for the new account

3.2 DB2 External Data Sources

  • CONTROL table — Queried twice during account number assignment. The <SORTCODE>-ACCOUNT-LAST row supplies the current highest account number, and <SORTCODE>-ACCOUNT-COUNT supplies the current total account count. Both are incremented and written back via UPDATE.
  • ACCOUNT table — Target of a DB2 INSERT in WRITE-ACCOUNT-DB2. All column values originate from COMMAREA fields and internally derived values.
  • PROCTRAN table — Target of a DB2 INSERT in WRITE-PROCTRAN-DB2. Records the successfully processed account-creation transaction.

3.3 Static / Configuration Inputs

  • SORTCODE (SORTCODE copybook) — The bank’s sort code, injected via the COPY SORTCODE copybook. Used to construct the NCS resource name (BANKZACCT + sort code), build DB2 CONTROL table lookup keys, and populate sort code columns in ACCOUNT and PROCTRAN inserts.

3.4 CICS Runtime Inputs

  • CICS date/time (via ASKTIME / FORMATTIME) — Obtained at runtime. The current date is used as the account-opened date and last-statement date. Adding 30 days produces the next-statement date (WS-FUTURE-DATE).

5. Processing Logic

5.1 High-Level Summary

CREACC applies a strict sequential validation funnel — customer existence → account count → account type — before acquiring the ENQ lock. Only after all business rules pass does the program engage the NCS resource lock and perform DB2 writes. This fail-fast pattern minimises resource contention in high-concurrency environments.

5.3 Step-by-Step Execution

Step 1 — Initialisation The program begins in the PREMIERE section. It copies the bank’s sort code into working-storage keys, zeroes the ACCOUNT-NUMBER field, and initialises the INQCUST-COMMAREA before any external calls are made.

Step 2 — Customer Existence Validation COMM-CUSTNO is moved into INQCUST-CUSTNO and a CICS LINK is issued to INQCUST. On return, both EIBRESP and INQCUST-INQ-SUCCESS are checked. If either is abnormal or non-'Y': COMM-SUCCESS = 'N', COMM-FAIL-CODE = '1', and execution terminates immediately.

Step 3 — Account Count Check CUSTOMER-ACCOUNT-COUNT links to INQACCCU to retrieve the count of existing accounts. Three sub-conditions are checked in sequence:

Condition Fail Code Meaning
CICS RESP not NORMAL '9' LINK itself failed
COMM-SUCCESS in INQACCCU-COMMAREA = 'N' '9' INQACCCU reported a business error
NUMBER-OF-ACCOUNTS > 9 '8' Customer already holds the maximum 9 accounts

Step 4 — Account Type Validation COMM-ACC-TYPE is validated against an explicit whitelist using an EVALUATE TRUE construct. Valid types are: ISA, MORTGAGE, SAVING, CURRENT, LOAN. Any other value sets COMM-SUCCESS = 'N' and COMM-FAIL-CODE = 'A'.

Step 5 — Serialise Account Number Assignment The NCS resource name is constructed as 'BANKZACCT' concatenated with the bank’s sort code (e.g., BANKZACCT987654). A CICS ENQ on this 16-byte resource name prevents concurrent account creation from producing duplicate account numbers. ENQ failure → COMM-FAIL-CODE = '3'.

Step 6 — Determine Next Account Number FIND-NEXT-ACCOUNT performs four DB2 operations under the exclusive ENQ lock. DB2 failures here are fatal and trigger ABNDPROC linkage followed by EXEC CICS ABEND ABCODE('HNCS'):

  1. SELECT CONTROL where CONTROL_NAME = '<sortcode>-ACCOUNT-LAST'
  2. Increment HV-CONTROL-VALUE-NUM by 1 → propagated to ACCOUNT-NUMBER and NCS-ACC-NO-VALUE
  3. UPDATE CONTROL to persist the new last account number
  4. SELECT + UPDATE CONTROL for <sortcode>-ACCOUNT-COUNT

Step 7 — Write Account to DB2 All host variables are populated from the COMMAREA and computed dates. CALCULATE-DATES sets ACCOUNT_OPENED and ACCOUNT_LAST_STATEMENT to today, and computes ACCOUNT_NEXT_STATEMENT as today + 30 days (with leap-year awareness for February). An EXEC SQL INSERT INTO ACCOUNT is then executed. If SQLCODE ≠ 0: COMM-FAIL-CODE = '7', DEQ is performed, then exit.

Step 8 — Write Processed Transaction Audit Record On a successful ACCOUNT INSERT, a PROCTRAN record of type 'OCA' (Open Current Account) is written with a zero amount. If the PROCTRAN INSERT fails, DEQ is performed, ABNDPROC is linked to, and EXEC CICS ABEND ABCODE('HWPT') is issued.

Step 9 — Release Serialisation and Return DEQ-NAMED-COUNTER releases the ENQ lock. The COMMAREA is populated with the final account details: COMM-SUCCESS = 'Y', COMM-EYECATCHER = 'ACCT', COMM-FAIL-CODE = ' ', and all date and account number fields. EXEC CICS RETURN terminates the task.

6. Business Rules

6.1 Customer Existence Validation

Before any account is created, the program performs a CICS LINK to INQCUST. If the CICS link does not return DFHRESP(NORMAL), or if INQCUST-INQ-SUCCESS is not equal to 'Y', processing is immediately halted with COMM-FAIL-CODE = '1'.

COBOL 
IF EIBRESP IS NOT EQUAL TO DFHRESP(NORMAL)
              OR INQCUST-INQ-SUCCESS IS NOT EQUAL TO 'Y'

              MOVE 'N' TO COMM-SUCCESS IN DFHCOMMAREA
              MOVE '1' TO COMM-FAIL-CODE IN DFHCOMMAREA

              PERFORM GET-ME-OUT-OF-HERE

           END-IF

6.2 Maximum Account Limit Enforcement

A customer is not permitted to hold more than 9 accounts simultaneously. If NUMBER-OF-ACCOUNTS exceeds 9, account creation is rejected with COMM-FAIL-CODE = '8'.

COBOL 
IF NUMBER-OF-ACCOUNTS IN INQACCCU-COMMAREA > 9
              DISPLAY 'CREACC: Customer has too many accounts (>9)'
              MOVE 'N' TO COMM-SUCCESS IN DFHCOMMAREA
              MOVE '8' TO COMM-FAIL-CODE IN DFHCOMMAREA

              PERFORM GET-ME-OUT-OF-HERE
           END-IF

6.3 Account Type Validation

Only five account types are permitted. An EVALUATE TRUE construct enforces an explicit whitelist. Any unrecognised type is rejected with COMM-FAIL-CODE = 'A'.

COBOL 
EVALUATE TRUE
           WHEN COMM-ACC-TYPE IN DFHCOMMAREA(1:3) = 'ISA'
           WHEN COMM-ACC-TYPE IN DFHCOMMAREA(1:8) = 'MORTGAGE'
           WHEN COMM-ACC-TYPE IN DFHCOMMAREA(1:6) = 'SAVING'
           WHEN COMM-ACC-TYPE IN DFHCOMMAREA(1:7) = 'CURRENT'
           WHEN COMM-ACC-TYPE IN DFHCOMMAREA(1:4) = 'LOAN'
                MOVE 'Y' TO COMM-SUCCESS OF DFHCOMMAREA
           WHEN OTHER
                MOVE 'N' TO COMM-SUCCESS OF DFHCOMMAREA
                MOVE 'A' TO COMM-FAIL-CODE IN DFHCOMMAREA
           END-EVALUATE.

6.4 Next Statement Date Calculation (Today + 30 Days)

The next statement date is always calculated as 30 days from the account opening date. Full Gregorian leap-year rules are applied for February: divisible by 4 but not 100, or divisible by 400. This calculation is mandatory and cannot be overridden by the caller.

COBOL 
EVALUATE WS-ORIG-DATE-MM
           WHEN 1
           WHEN 3
           WHEN 5
           WHEN 7
           WHEN 8
           WHEN 10
           WHEN 12
                COMPUTE WS-INTEGER = WS-INTEGER + 30
           WHEN 9
           WHEN 4
           WHEN 6
           WHEN 11
                COMPUTE WS-INTEGER = WS-INTEGER + 30
           WHEN 2
                COMPUTE WS-INTEGER = WS-INTEGER + 28
                DIVIDE WS-ORIG-DATE-YYYY BY 4 GIVING DONT-CARE
                   REMAINDER LEAP-YEAR

                IF LEAP-YEAR = ZERO
                   DIVIDE WS-ORIG-DATE-YYYY BY 100 GIVING DONT-CARE
                      REMAINDER LEAP-YEAR

                   IF LEAP-YEAR > 0
                      ADD 1 TO WS-INTEGER GIVING WS-INTEGER
                   ELSE
                      DIVIDE WS-ORIG-DATE-YYYY BY 400 GIVING DONT-CARE
                         REMAINDER LEAP-YEAR
                      IF LEAP-YEAR = ZERO
                         ADD 1 TO WS-INTEGER GIVING WS-INTEGER
                      END-IF
                   END-IF
                END-IF

           END-EVALUATE.

6.5 Next Sequential Account Number Assignment

Account numbers are assigned sequentially by incrementing the last known value by 1 from the CONTROL table. The CONTROL table is updated immediately to reserve the new account number and prevent duplicate assignment.

COBOL

                 COMM-NUMBER
                 ACCOUNT-NUMBER
                 REQUIRED-ACCT-NUMBER3

                 HV-CONTROL-VALUE-NUM

7. Program Paragraphs

7.1 P010 — Main Entry Point and Orchestration

Acts as the primary controller for the account creation workflow. Initialises key working-storage fields, orchestrates all validation calls, and sequences the ENQ, DB2 operations, and DEQ. All major business logic is delegated to sub-paragraphs: CUSTOMER-ACCOUNT-COUNT, ACCOUNT-TYPE-CHECK, ENQ-NAMED-COUNTER, FIND-NEXT-ACCOUNT, WRITE-ACCOUNT-DB2, and GET-ME-OUT-OF-HERE.

7.2 ENQ-NAMED-COUNTER — Enqueue Named Counter Resource

Serialises concurrent access to the account number sequence by acquiring an exclusive CICS ENQ on the NCS resource BANKZACCT<SORTCODE>. Constructs the 16-byte resource name by moving SORTCODE into NCS-ACC-NO-TEST-SORT. If the ENQ fails, sets COMM-FAIL-CODE = '3' and terminates.

7.3 DEQ-NAMED-COUNTER — Dequeue Named Counter Resource

Releases the CICS ENQ acquired by ENQ-NAMED-COUNTER. Called on both the success path (after writing PROCTRAN) and error paths (after a failed ACCOUNT or PROCTRAN INSERT) to ensure the lock is always released. DEQ failure sets COMM-FAIL-CODE = '5'.

7.4 FIND-NEXT-ACCOUNT — Determine and Reserve the Next Account Number

Reads and increments the SORTCODE-ACCOUNT-LAST counter under the exclusive ENQ lock. Also reads and increments SORTCODE-ACCOUNT-COUNT. Any DB2 failure (non-zero SQLCODE on any SELECT or UPDATE) triggers ABNDPROC linkage followed by CICS ABEND ABCODE('HNCS') — these are treated as unrecoverable.

7.5 WRITE-ACCOUNT-DB2 — Populate and Insert Account Row into DB2

Constructs the full HOST-ACCOUNT-ROW from COMMAREA and computed date values, then inserts it into the DB2 ACCOUNT table. Calls CALCULATE-DATES for date population, independently recomputes the next-statement date using COBOL intrinsic functions, and stages STORED-* fields for PROCTRAN use. On INSERT failure, sets COMM-FAIL-CODE = '7', calls DEQ-NAMED-COUNTER, and exits gracefully.

7.6 WRITE-PROCTRAN — Processed Transaction Write Dispatcher

A thin wrapper that delegates directly to WRITE-PROCTRAN-DB2 via a single PERFORM. Provides a logical separation point allowing the PROCTRAN write mechanism to be swapped or extended without modifying the caller.

7.7 WRITE-PROCTRAN-DB2 — Insert Processed Transaction Record into DB2

Records the account creation event as an audit entry in the DB2 PROCTRAN table. Obtains the current timestamp via CICS ASKTIME / FORMATTIME, constructs the 40-byte HV-PROCTRAN-DESC field, and sets transaction type to 'OCA' with amount zero. PROCTRAN INSERT failure triggers DEQ, ABNDPROC linkage, and CICS ABEND ABCODE('HWPT').

7.8 GET-ME-OUT-OF-HERE — Program Termination

The single exit point for the program, regardless of success or failure. Issues EXEC CICS RETURN to return control to CICS with the populated (or failure-flagged) COMMAREA. All error paths and the normal success path converge here.

7.9 CUSTOMER-ACCOUNT-COUNT — Retrieve Existing Account Count via INQACCCU

Prepares and issues a CICS LINK SYNCONRETURN to INQACCCU. Sets the sentinel value of 20 in NUMBER-OF-ACCOUNTS before the call (ensuring that a silent INQACCCU failure will be detected by the subsequent > 9 check). The CICS RESP, INQACCCU COMM-SUCCESS, and account count are all evaluated by the caller P010.

COBOL 
MOVE 20 TO NUMBER-OF-ACCOUNTS IN INQACCCU-COMMAREA.
           MOVE COMM-CUSTNO IN DFHCOMMAREA
              TO CUSTOMER-NUMBER IN INQACCCU-COMMAREA.

           SET COMM-PCB-POINTER TO NULL

           EXEC CICS LINK PROGRAM('INQACCCU')
                COMMAREA(INQACCCU-COMMAREA)
                RESP(WS-CICS-RESP)
                SYNCONRETURN
                END-EXEC.

7.10 CALCULATE-DATES — Derive Account Date Fields

Obtains the current absolute time via CICS ASKTIME and formats it via CICS FORMATTIME. Converts today’s date to an integer using FUNCTION INTEGER-OF-DATE, applies the 30-day (or February-specific) addition, converts the result back to Gregorian using FUNCTION DATE-OF-INTEGER, and populates all three DB2 host variable date groups for HV-ACCOUNT-OPENED, HV-ACCOUNT-LAST-STMT, and HV-ACCOUNT-NEXT-STMT.

7.11 ACCOUNT-TYPE-CHECK — Validate the Requested Account Type

Enforces the business rule that only five permitted account types may be created. Uses an EVALUATE TRUE construct testing COMM-ACC-TYPE against leading characters. A valid type sets COMM-SUCCESS = 'Y'; any unrecognised type sets COMM-SUCCESS = 'N' and COMM-FAIL-CODE = 'A'.

7.12 POPULATE-TIME-DATE2 — Capture Current Date and Time for Abend Diagnostics

A utility paragraph used exclusively to populate accurate timestamps into ABNDINFO-REC before any fatal abend. Issues CICS ASKTIME and CICS FORMATTIME to capture WS-ORIG-DATE (DDMMYYYY) and WS-TIME-NOW (HHMMSS). Called from error-handling blocks in FIND-NEXT-ACCOUNT and WRITE-PROCTRAN-DB2.

9. Error Handling

9.1 COMM-FAIL-CODE Reference

Code Meaning Recovery
' ' Success N/A
'1' Customer not found (INQCUST failed or returned not-found) Graceful return — no DB2 operations attempted
'3' CICS ENQ on Named Counter failed Graceful return — no DB2 operations attempted
'5' CICS DEQ on Named Counter failed Graceful return
'7' DB2 INSERT into ACCOUNT table failed Graceful return — DEQ performed before exit
'8' Customer already holds 9 or more accounts Graceful return — no DB2 operations attempted
'9' Error retrieving account count from INQACCCU Graceful return — no DB2 operations attempted
'A' Invalid account type supplied Graceful return — no DB2 operations attempted

9.2 Business Rule Validation Errors

All business rule failures follow the same pattern: set COMM-SUCCESS = 'N', set the appropriate COMM-FAIL-CODE, and route to GET-ME-OUT-OF-HERE. No DB2 operations are attempted once a validation failure is detected.

9.3 CICS Resource Lock Errors

  • ENQ failure (COMM-FAIL-CODE = '3'): Detected in ENQ-NAMED-COUNTER by checking WS-CICS-RESP against DFHRESP(NORMAL). The program exits without any DB2 writes.
  • DEQ failure (COMM-FAIL-CODE = '5'): Detected in DEQ-NAMED-COUNTER. This section is invoked on both the success path and error cleanup paths to guarantee the lock is always released.

9.4 DB2 Operation Error Handling

The following table summarises DB2 error handling behaviour. Note the critical distinction between graceful returns and fatal abends:

Operation Failure Handling Abend Code
SELECT CONTROL (ACCOUNT-LAST) ABNDPROC link + CICS ABEND HNCS
UPDATE CONTROL (ACCOUNT-LAST) ABNDPROC link + CICS ABEND HNCS
SELECT CONTROL (ACCOUNT-COUNT) ABNDPROC link + CICS ABEND HNCS
UPDATE CONTROL (ACCOUNT-COUNT) ABNDPROC link + CICS ABEND HNCS
INSERT ACCOUNT Graceful: COMM-FAIL-CODE = '7', DEQ, return None
INSERT PROCTRAN DEQ + ABNDPROC link + CICS ABEND HWPT

The ACCOUNT INSERT is the only DB2 failure that results in a graceful return to the caller. All CONTROL table and PROCTRAN failures are treated as unrecoverable because they indicate data integrity issues in the account sequencing and audit infrastructure.

9.5 Structured Abend Escalation

For all fatal DB2 errors, CREACC follows a consistent structured pattern before issuing the CICS ABEND:

  1. Initialise ABNDINFO-REC
  2. Populate ABND-RESPCODE and ABND-RESP2CODE from EIBRESP and EIBRESP2
  3. Retrieve CICS application identifier via EXEC CICS ASSIGN APPLID
  4. Capture task number (EIBTASKN), transaction ID (EIBTRNID), and absolute timestamp via POPULATE-TIME-DATE2
  5. Assemble a free-form message identifying the failing paragraph and DB2 error
  6. Issue EXEC CICS LINK to ABNDPROC with ABNDINFO-REC as COMMAREA
  7. Issue EXEC CICS ABEND ABCODE('HNCS') or ABCODE('HWPT')

The two distinct abend codes enable operations teams to triage production failures by abend code without reading diagnostic dumps: HNCS indicates a sequencing/CONTROL table failure, HWPT indicates an audit trail write failure.

9.6 Diagnostic Logging via DISPLAY

Throughout execution, DISPLAY statements emit progress and diagnostic messages to the CICS system log, including:

  • Customer number received on entry
  • INQCUST and INQACCCU response values and account counts
  • SQLCODE values from each DB2 operation
  • Current and new counter values from the CONTROL table
  • On PROCTRAN INSERT failure: full RESP/RESP2 codes and complete HOST-PROCTRAN-ROW content

9.7 Controlled Program Termination

GET-ME-OUT-OF-HERE is the single exit point for all code paths — success and failure alike. It issues a single EXEC CICS RETURN, ensuring the calling program always receives a consistently populated COMMAREA with COMM-SUCCESS and COMM-FAIL-CODE accurately reflecting the outcome.

10. Constraints

10.1 Input Validation Constraints

  • Customer number must reference an existing customer — Validated via INQCUST before any other processing. Fail code '1' on rejection.
  • Account type must be one of five permitted values — ISA, MORTGAGE, SAVING, CURRENT, or LOAN only. Fail code 'A' on rejection.

10.2 Business Rule Constraints

  • A customer may hold no more than 9 accounts — The initial sentinel value of NUMBER-OF-ACCOUNTS = 20 ensures that a silent INQACCCU failure will itself trigger a rejection.
  • Next statement date is always set to today plus 30 days — This calculation is mandatory and cannot be overridden by the caller. Full Gregorian leap-year rules are applied for February.

10.3 Sequencing and Ordering Constraints

The following strict execution order must be maintained:

  1. Customer existence validation (INQCUST) — before all other processing
  2. Account count check (INQACCCU) — before account type check
  3. Account type validation — before ENQ acquisition
  4. ENQ acquisition — before CONTROL table reads
  5. CONTROL table read and update — before ACCOUNT INSERT
  6. ACCOUNT INSERT — before PROCTRAN INSERT
  7. DEQ — after all DB2 operations (or as part of error cleanup)

10.4 Resource and Concurrency Constraints

  • The CICS ENQ on NCS-ACC-NO-NAME ('BANKZACCT' + SORTCODE) serialises all concurrent account number assignments. The lock is held for the minimum required period — from just before CONTROL table access until after the ACCOUNT INSERT completes.
  • DEQ must always be issued, whether the processing succeeded or failed, to prevent deadlock conditions for subsequent account creation requests.

10.5 Output Constraints

  • COMMAREA eyecatcher is always 'ACCT' on success.
  • Date fields in the returned COMMAREA are always in DDMMYYYY format (8 characters, no delimiters).
  • PROCTRAN description field layout is fixed: customer number (1–10), account type (11–18), last statement date (19–26), next statement date (27–34), spaces (35–40).

10.6 Configuration Constraints

SORTCODE is defined as PIC 9(6) VALUE 987654 in the SORTCODE copybook. This is a compile-time configuration that constrains the program to a single institution’s sort code. A modernisation pathway would externalise this to a CICS resource definition or environment variable.

11. Examples

11.1 Example 1 — Successful Account Creation

Input (COMMAREA fields):

Field Value
COMM-CUSTNO 0000000042
COMM-ACC-TYPE CURRENT
COMM-INT-RT 1.50
COMM-OVERDR-LIM 500
COMM-AVAIL-BAL 1000.00
COMM-ACT-BAL 1000.00

Pre-conditions: Customer 0000000042 exists, holds 2 accounts, CONTROL table ACCOUNT-LAST = 00000099, today’s date = 15.06.2025.

Processing:

  1. INQCUST → customer found (INQCUST-INQ-SUCCESS = 'Y')
  2. INQACCCU → account count = 2 (≤ 9, proceed)
  3. Account type CURRENT → valid
  4. CICS ENQ on BANKZACCT987654 → granted
  5. CONTROL SELECT → ACCOUNT-LAST = 99 → increment to 100 → UPDATE
  6. CONTROL SELECT → ACCOUNT-COUNT = 250 → increment to 251 → UPDATE
  7. INSERT ACCOUNT → ACCOUNT_NUMBER = 00000100, ACCOUNT_NEXT_STATEMENT = 15.07.2025
  8. INSERT PROCTRAN → type OCA, amount 0
  9. CICS DEQ released

Output (COMMAREA fields returned):

Field Value
COMM-SUCCESS Y
COMM-FAIL-CODE (space)
COMM-NUMBER 00000100
COMM-SORTCODE 987654
COMM-OPENED 15062025
COMM-LAST-STMT-DT 15062025
COMM-NEXT-STMT-DT 15072025

11.2 Example 2 — Failure: Customer Not Found

Input: COMM-CUSTNO = 0000009999, COMM-ACC-TYPE = SAVING

Processing: INQCUST cannot locate the customer → INQCUST-INQ-SUCCESS = 'N'. No account count check, type check, ENQ, or DB2 operations are attempted.

Output:

Field Value
COMM-SUCCESS N
COMM-FAIL-CODE 1

11.3 Example 3 — Failure: Too Many Accounts

Input: COMM-CUSTNO = 0000000007, COMM-ACC-TYPE = ISA

Pre-conditions: Customer exists, currently holds 10 accounts.

Processing: INQCUST succeeds. INQACCCU returns NUMBER-OF-ACCOUNTS = 10. The check IF NUMBER-OF-ACCOUNTS > 9 triggers. No type check, ENQ, or DB2 operations are attempted.

Output:

Field Value
COMM-SUCCESS N
COMM-FAIL-CODE 8

11.4 Example 4 — Failure: Invalid Account Type

Input: COMM-CUSTNO = 0000000015, COMM-ACC-TYPE = PREMIUM

Pre-conditions: Customer exists, holds 1 account.

Processing: INQCUST succeeds. INQACCCU returns count = 1. ACCOUNT-TYPE-CHECK finds PREMIUM is not in the permitted whitelist. No ENQ, no DB2 insert, no PROCTRAN write are performed.

Output:

Field Value
COMM-SUCCESS N
COMM-FAIL-CODE A
