Grub Workflow

1. Overview

GRUB (Git Remote User Build) is a development tool that synchronizes local file changes directly to z/OS USS (Unix System Services) and automatically runs the setup or pipeline scripts upon completion. Unlike traditional Git-based workflows, no commit or push to a remote repository is required — GRUB transfers only the files that have changed, making it the fastest option for iterative development on the Bank of Z platform.

This workflow is ideal for developers who need rapid feedback cycles when modifying COBOL programs, BMS maps, z/OS Connect API assets, or configuration files.

Prerequisites: Before using this workflow, complete the GRUB Setup steps to configure your environment.

2. System Architecture

The GRUB workflow operates across two environments: your local machine and z/OS USS. GRUB acts as the bridge between them, computing a patch of local changes and applying it to the remote USS environment without any intermediate Git operations.

The diagram above illustrates the end-to-end flow from a developer triggering a sync on their local machine through to the Bank of Z frontend being live on z/OS. The key architectural advantage is that only a patch file — not the entire repository — travels over the wire. Once applied to USS, the native setup-remote.sh script handles all deployment stages without any Zowe CLI overhead or GitHub connectivity.

3. GRUB Setup and Configuration

3.1 Install GRUB

Follow the GRUB installation instructions for your specific environment. GRUB is available from the IBM Z development tooling portfolio.

3.2 Configure GRUB for Bank of Z

After installing GRUB, configure it with the following settings:

Setting Description Example Value
Remote host Hostname or IP address of your z/OS USS system myzos.example.com
Remote user Your USS user ID IBMUSER
Remote path Path where the Bank of Z repository is synchronized on USS /usr/local/sandboxes/bank-of-z/Bank-of-Z
Post-sync command Command GRUB runs on USS after each synchronization bash <remote-path>/.setup/setup-remote.sh

Note: The Remote path should match the sandbox.path value defined in .setup/config/config.yaml with /Bank-of-Z appended.

3.3 Post-Sync Command

The post-sync command is the critical hook that automates your deployment after every sync. Configure it as follows, replacing <remote-path> with your actual remote path:

BASH 
bash /usr/local/sandboxes/bank-of-z/Bank-of-Z/.setup/setup-remote.sh

Refer to the GRUB documentation for the configuration procedure specific to your installed version.

4. Daily Development Cycle

The GRUB workflow follows a streamlined four-step cycle that removes the commit/push overhead from your development loop.

graph LR A[1. Make Changes Locally] --> B[2. Trigger GRUB Sync] B --> C[3. Automatic Setup Runs on USS] C --> D[4. Validate in Browser] D --> A style A fill:#0062ff,color:#fff style B fill:#393939,color:#fff style C fill:#6929c4,color:#fff style D fill:#198038,color:#fff

4.1 Make Changes

Modify application source code in your local workspace. No Git commit is required. Common file types you may modify include:

  • COBOL programs and copybooks
  • BMS maps
  • z/OS Connect API assets
  • Configuration files

4.2 Trigger a GRUB Sync

Trigger a GRUB sync from your local machine using the command or UI action specific to your GRUB installation. GRUB will:

  1. Analyze your local file changes since the previous sync
  2. Create a patch file containing only the modified content
  3. Transfer the patch to z/OS USS and apply it to the Bank-of-Z directory

Because only changed files are transferred, subsequent syncs after the initial deployment are significantly faster than a full setup.

4.3 What Runs Automatically

Once the patch is applied on USS, the post-sync hook fires setup-remote.sh automatically. The following diagram shows the sequence of operations:

GRUB detects that it is running from within the Bank-of-Z repository and uses the synced files directly — no re-cloning occurs. This is what makes subsequent syncs significantly faster than a full setup.

4.4 Validate Changes

Open the Bank of Z frontend in your browser to verify your changes are live:

CODE 
http://<your-zos-host>:9080/bank-frontend-vanilla

5. Stage Detection Mechanism

A key part of what makes GRUB syncs fast on subsequent runs is the stage detection logic built into setup-remote.sh. When the script runs on USS after a GRUB sync, it checks whether it is executing from within the Bank-of-Z repository. If it is, it uses that location directly instead of attempting a fresh clone from GitHub.

graph TD A[setup-remote.sh starts] --> B{Is this a Git repository?} B -- No --> C[Clone from GitHub] B -- Yes --> D{repo name == Bank-of-Z?} D -- No --> C D -- Yes --> E[Use current repo location as BANK_DIR] E --> F[Run setup stages with synced files] C --> F style E fill:#198038,color:#fff style F fill:#0062ff,color:#fff

This detection is implemented with the following Bash logic inside setup-remote.sh:

BASH 
if git rev-parse --git-dir > /dev/null 2>&1; then
    local repo_name=$(basename "$(git rev-parse --show-toplevel)")
    if [[ "$repo_name" == "Bank-of-Z" ]]; then
        # GRUB workflow — use current repository location
        BANK_DIR="$(git rev-parse --show-toplevel)"
    fi
fi

This means your uncommitted local changes are used as-is, and no clone from GitHub is attempted. This behavior is specific to the GRUB workflow and is what enables the offline capability — no GitHub connectivity is needed after the initial clone.

6. Why Use GRUB

The following table summarizes the key benefits of the GRUB workflow compared to alternatives:

Feature Benefit
No commits required Test changes immediately without a Git commit or push
Patch-based sync Only changed files are transferred — fast incremental updates
Automatic setup Environment is ready as soon as the sync completes
Native execution Runs directly on USS — no Zowe CLI overhead
Works offline No GitHub connectivity needed after initial clone
