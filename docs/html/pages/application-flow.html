Application Flow

Bank of Z uses a hybrid architecture that combines a modern web interface with IBM Z transaction-processing systems. Banking requests are submitted through a browser-based application and processed by either CICS or IMS Transaction Manager (IMS TM), depending on the customer identifier. This document describes the end-to-end transaction and data flow through all layers of the application, from the user interface down to the core mainframe services and databases.

1. Overview

The Bank of Z application bridges modern web-based banking with the reliability and throughput of IBM Z transaction-processing environments. A single browser-based UI serves as the entry point for all customer interactions. Beneath the surface, routing logic determines whether a given request flows through CICS or IMS TM, enabling the platform to support multiple IBM Z technologies while presenting a consistent experience to the end user.

For selected operations, Bank of Z extends this architecture further by integrating with external banking systems through IBM MQ, enabling inbound money transfer requests and other cross-institution workflows.

Key characteristics of the architecture:

  • Hybrid routing: Requests are directed to CICS or IMS TM based on customer identifier prefix.
  • REST-based middleware: z/OS Connect acts as the bridge between the web tier and the mainframe transaction layer.
  • Atomic transactions: Core services such as account creation execute as a single CICS task, with ENQ/DEQ locking, Db2 writes, and audit trail generation all occurring within one execution unit.
  • Immutable audit trail: Every significant transaction writes a record to the PROCTRAN Db2 table, supporting regulatory reporting and reconciliation.
  • External integration: IBM MQ enables asynchronous communication with external banking systems.

2. System Architecture

The Bank of Z system is composed of four logical tiers: the web presentation layer, the API and integration layer, the transaction-processing layer, and the data layer. The diagram below illustrates how these tiers relate to one another and identifies the key components within each.

The four tiers work together as follows:

  • The Web Tier captures user intent and applies routing logic before dispatching requests.
  • The Integration Layer (z/OS Connect) translates REST API calls into the protocol expected by CICS or IMS TM, and IBM MQ handles asynchronous external messaging.
  • The Transaction Processing Layer executes business logic — CICS-hosted COBOL programs such as CREACC handle account provisioning, while IMS TM handles IMS-routed customers.
  • The Data Layer stores all persistent records across Db2 tables (ACCOUNT, PROCTRAN, CONTROL, CUSTOMER) and IMS databases.

3. Request Processing Flow

3.1 Step-by-Step Flow

A typical banking request follows this sequence of steps:

  1. A user performs a banking operation through the Bank of Z UI.
  2. The Bank of Z UI determines the appropriate transaction-processing path based on the customer identifier prefix (C → CICS, I → IMS TM).
  3. The Bank of Z UI sends the request to z/OS Connect through a REST API call.
  4. z/OS Connect forwards the request to the selected transaction-processing environment.
  5. CICS or IMS TM executes the required business logic and accesses the appropriate data sources.
  6. Data is retrieved from or written to the corresponding Db2 or IMS database, depending on the processing path and operation.
  7. The transaction result is returned through z/OS Connect to the Bank of Z UI.
  8. The Bank of Z UI displays the result to the user.

4. Routing Logic

4.1 Customer Identifier-Based Routing

Bank of Z routes requests to different transaction-processing environments based on the customer identifier pattern. This model demonstrates how multiple IBM Z transaction-processing technologies can be integrated into a single application while maintaining a consistent user experience.

Customer Identifier Pattern Processing Environment
Cnnnn (e.g. C1234) CICS
Innn (e.g. I1234) IMS TM

For example:

  • A customer with identifier C1234 is routed through the CICS application path, where COBOL programs execute against Db2 tables.
  • A customer with identifier I1234 is routed through the IMS TM application path, where transactions execute against IMS databases.

5. CICS Transaction Processing — Account Creation Example

5.1 CREACC Service Overview

CREACC is a representative CICS-hosted COBOL program that illustrates how the Bank of Z transaction layer handles a complex, multi-step business operation. It implements the bank account creation transaction and is responsible for:

  • Validating the customer record.
  • Sequencing a new account number using a CICS ENQ/DEQ-protected counter.
  • Persisting the account record to Db2.
  • Writing an immutable audit record to the PROCTRAN table.

All of this occurs within a single CICS task execution, ensuring atomicity.

“Enqueue the Named Counter for ACCOUNT, increment the counter and take the new account number, & attempt to update the ACCOUNT datastore on DB2. If that is successful, write a rec to the PROCTRAN datastore.”

5.4 Validation Pipeline

CREACC applies a strict sequential validation funnel before acquiring any locks or writing any data:

  1. Customer existence check — Links to INQCUST with COMM-CUSTNO. Failure sets COMM-FAIL-CODE = '1'.
  2. Account count limit check — Links to INQACCCU. Error retrieving count sets COMM-FAIL-CODE = '9'. Count exceeding 9 sets COMM-FAIL-CODE = '8'.
  3. Account type validation — COMM-ACC-TYPE must be one of: ISA, MORTGAGE, SAVING, CURRENT, LOAN. Invalid type sets COMM-FAIL-CODE = 'A'.

Only after all three gates pass does the program acquire the ENQ lock and proceed to sequence and write the account. This fail-fast pattern minimises resource contention in high-concurrency environments.

5.5 Account Number Sequencing

The program implements a distributed sequence generator using CICS ENQ/DEQ and the Db2 CONTROL table:

COBOL 
* Construct the NCS resource name
MOVE 'BANKZACCT' TO NCS-ACC-NO-NAME-PRFX
MOVE SORTCODE    TO NCS-ACC-NO-NAME-SUFX

* Acquire exclusive lock
EXEC CICS ENQ RESOURCE(NCS-ACC-NO-NAME) ...

* Read current sequence value
EXEC SQL SELECT ACCOUNT_LAST
         INTO :HV-ACCOUNT-LAST
         FROM CONTROL
         WHERE SORTCODE = :HV-SORTCODE
END-EXEC

* Increment and persist
ADD 1 TO HV-ACCOUNT-LAST
EXEC SQL UPDATE CONTROL
         SET ACCOUNT_LAST = :HV-ACCOUNT-LAST
         WHERE SORTCODE = :HV-SORTCODE
END-EXEC

* Release lock after DB2 INSERT
EXEC CICS DEQ RESOURCE(NCS-ACC-NO-NAME) ...

The ENQ resource name incorporates the sort code (BANKZACCT + 987654), making the lock scope institution-specific and supporting potential multi-bank deployments.

5.6 Date Calculations

  • Account Opened / Last Statement Date: Derived from today’s date using CICS ASKTIME and FORMATTIME.
  • Next Statement Date: Calculated as today + 30 days using INTEGER-OF-DATE / DATE-OF-INTEGER intrinsic COBOL functions, with full leap-year logic applied for February (÷4, ÷100, ÷400 algorithm).

5.7 Audit Trail

Every successful account creation produces a PROCTRAN record of type OCA (Branch Create Account). This record captures:

Field Value
Transaction type OCA (Branch Create Account)
Timestamp CICS ASKTIME / FORMATTIME
Task reference CICS task number
Customer number COMM-CUSTNO
Account type COMM-ACC-TYPE
Last statement date Today’s date
Next statement date Today + 30 days
Footer flag CREATE

This provides a non-repudiable, time-stamped audit log fully decoupled from the ACCOUNT table, supporting regulatory reporting and event sourcing without modifying core account records.

5.8 COMM-FAIL-CODE Reference

Code Meaning
' ' Success
'1' Customer not found (INQCUST failed or returned not-found)
'3' CICS ENQ on Named Counter failed
'5' CICS DEQ on Named Counter failed
'7' Db2 INSERT into ACCOUNT table failed
'8' Customer already holds 9 or more accounts
'9' Error retrieving account count from INQACCCU
'A' Invalid account type supplied

6. External Integration

6.1 IBM MQ Integration

For selected operations, Bank of Z can exchange information with external systems through IBM MQ. This enables integration scenarios such as processing inbound money transfer requests from external banking applications.

sequenceDiagram participant EXT as External Banking Application participant MQ as IBM MQ participant CICS as CICS TS participant DB2 as IBM Db2 for z/OS EXT->>MQ: Put message (e.g. money transfer request) MQ->>CICS: Trigger transaction via MQ bridge CICS->>DB2: Process transaction, update balances DB2-->>CICS: Confirmation CICS-->>MQ: Put response message (optional) MQ-->>EXT: Return result to external system

IBM MQ acts as a durable, asynchronous intermediary, decoupling the timing of external requests from the internal transaction-processing cycle. This ensures that external banking applications can submit requests without requiring a synchronous connection to the mainframe.

7. Key Architectural Observations

7.1 Concurrency and Data Integrity

The ENQ/DEQ bracket wrapping the entire account number generation and Db2 write cycle in CREACC is a critical design choice. Because the CONTROL table acts as a shared sequence generator, concurrent CREACC tasks on the same CICS region could corrupt the sequence without this serialisation gate. The ENQ resource name incorporates the sort code (BANKZACCT987654), making the lock scope institution-specific.

7.2 Fail-Fast Validation Pattern

CREACC applies a strict sequential validation funnel — customer existence → account count → account type — before acquiring the ENQ lock. This minimises resource contention and improves throughput in high-concurrency environments, as invalid requests are rejected before any locking or Db2 write activity occurs.

7.3 Audit Trail Architecture

Every successful account creation produces a PROCTRAN record of type OCA. This provides a non-repudiable, time-stamped audit log fully decoupled from the ACCOUNT table, supporting regulatory reporting, reconciliation, and event sourcing without requiring changes to core account records.

7.4 Abend Code Taxonomy

CREACC uses two distinct abend codes to enable fast operational triage:

Abend Code Trigger Condition
HNCS Named Counter / CONTROL table failure
HWPT PROCTRAN write failure

This allows operations teams to distinguish the nature of a production failure by abend code alone, without reading diagnostic dumps.

7.5 Hard-Coded Sort Code

SORTCODE is defined as PIC 9(6) VALUE 987654 in the SORTCODE copybook. This is a configuration concern that constrains the program to a single institution’s sort code at compile time. A modernisation pathway would externalise this to a CICS resource definition or environment variable, enabling multi-tenant deployments.
